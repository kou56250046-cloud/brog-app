「この業務、AIエージェントにできないか」と相談されることが増えた。ところが話を聞いていくと、手順は毎回同じで、AI が要るのは途中の 1 か所だけ、ということがよくある。逆に、決まった手順のシステムを作ったあとで、想定外の問い合わせに対応できないと分かることもある。

どちらの失敗も、作る前の見分け方で防げる。この連載では、Workflow（決まった手順で処理する仕組み）と AIエージェント（状況を見て次の手を選ぶ仕組み）を**どう見分け、どう組み合わせるか**を 3 回で整理する。第 1 回のこの記事では、見分けるための考え方と判断基準を扱う。

> [!TIP] この記事で分かること
> - Workflow とエージェントを分ける軸は「処理の流れを誰が決めるか」であること
> - 同じ請求業務でも、登録は Workflow、理由の調査はエージェントになる理由（動くコード付き）
> - 二択ではなく「AI にどこまで任せるか」の 5 段階で考える方法
> - 「if 文が多いからエージェント」が誤りである理由と、逆にルールを AI に寄せるべき場合
> - 工程ごとに点数を付けて、Workflow・エージェント・ハイブリッドを判定するチェックリスト

エージェントそのものの仕組み（ループ・ツール・文脈）は「[AIエージェントは「賢さ」より「設計」で決まる](2026-09-29-ai-agent-design-fundamentals.html)」で書いた。この連載では、その記事で簡単に触れた「ワークフローとエージェントの違い」を、判断の道具として使えるところまで掘り下げる。内容は特定の AI サービスに依存しない。

## コードの読み方

コードはすべて Python で、外部のライブラリを使わずに動く。**本物の LLM の代わりに、決まった判断をする練習用の偽物**を使うので、API キーがなくても手元で動きを確かめられる。ほぼ全行に日本語の説明を付け、要点の行には `★` を付けた。

| 書き方 | 意味 |
|---|---|
| `# 〜` | 説明文（コメント）。プログラムとしては無視される |
| `def 名前(引数):` | 「関数」の定義。決まった手順に名前を付けたもの。**引数**はその手順に渡す材料 |
| `return 値` | 関数の結果として、その値を返して終わる |
| `if 条件:` | 条件に合うときだけ、下の字下げされた行を実行する |
| `for x in 並び:` | 並びの中身を 1 つずつ `x` に入れて繰り返す |
| `[a, b]` / `{"名前": 値}` | リスト（順番のある入れ物）/ 辞書（名前と値の組の入れ物） |
| `f"...{名前}..."` | `{}` の中に変数の値を埋め込んだ文字列 |

## 違いは「AI を使うか」ではなく「流れを誰が決めるか」

AI システムを設計するとき、最初に決めるべきことは 1 つだ。**処理の手順をあらかじめ決めておくべきか、それとも AI に状況を見て手順を選ばせるべきか。**

- **Workflow**：処理の手順を固定する。あらかじめ決めた順番と条件分岐に従って動く
- **AIエージェント**：目標だけを渡し、AI が必要な道具と手順を選び、結果を確かめながら進む

ここで間違えやすいのは、「AI を使っていればエージェント」と考えることだ。Workflow の途中で LLM を呼んでもよい。違いは、**次に何をするかを決めているのが、人間が書いたプログラムか、AI か**にある。

Anthropic は構築ガイドで、Workflow を「LLM とツールを、あらかじめ定義したコードの経路で動かすシステム」、エージェントを「LLM が自分の処理の進め方とツールの使い方を動的に決めるシステム」と定義している。ここでも線は「誰が経路を決めるか」に引かれている。

```flow caption="Workflow。LLM を使う工程があっても、道筋はプログラムが決めている"
A([請求書を受信]) --> B(項目を抜き出す\nLLM):::hl
B --> C[取引先を確かめる]
C --> D[金額で承認先を振り分ける]
D --> E([登録])
```

```flow caption="AIエージェント。次の一手を AI が選び、結果を見てまた選ぶ"
A([目標を受け取る]) --> B(次に何をするか決める\nLLM):::hl
B --> C[選んだ道具を実行]
C --> D{目標に届いた?}
D -- いいえ --> B
D -- はい --> E([回答])
```

2 つの図の違いは、矢印が戻るかどうかだ。Workflow は上から下へ一本道で流れる。エージェントは、結果を見て判断に戻るループを持つ。

| 観点 | Workflow | AIエージェント |
|---|---|---|
| 処理の流れ | 人間・プログラムが決める | AI が状況に応じて決める |
| 手順 | あらかじめ定義する | 実行しながら決まる |
| 分岐 | if / else などで書く | AI が判断する |
| 道具の選択 | あらかじめ決まっている | AI が選ぶ |
| 繰り返し | 回数・条件を決めておく | AI が必要に応じて繰り返す |
| 予測しやすさ | 高い | 相対的に低い |
| 柔軟さ | 低い | 高い |

> [!NOTE] 呼び名の揺れ
> 日本語の技術記事では「ワークフロー型」「エージェント型」という対比がよく使われる。英語の「agentic workflow（エージェント的なワークフロー）」は、書き手によって「LLM を組み込んだ Workflow」の意味にも「エージェント」の意味にもなる。この連載では、流れを決めるのがプログラムなら Workflow、AI ならエージェントと呼ぶ。

## 同じ「請求」でも、登録は Workflow、理由の調査はエージェント

違いを、同じ請求業務の 2 つの仕事で確かめる。1 つ目は「届いた請求書を読んで登録する」仕事だ。何が届いても、抜き出す → 確かめる → 振り分ける → 登録する、の順番は変わらない。

```python title="invoice_workflow.py" caption="請求書の登録。LLM を使うのは抽出の 1 か所だけで、道筋はプログラムが決めている"
import re  # 文字列から決まった形を探す道具（正規表現）

VENDORS = {"青葉商事", "北斗製作所"}  # 登録済みの取引先。集合（重複のない入れ物）


def fake_llm_extract(text: str) -> dict:
    """★ LLM の出番はここだけ。自由な文面から取引先と金額を抜き出す（練習用の偽物）。"""
    vendor = re.search(r"^(\S+?)より", text).group(1)  # 「◯◯より」の◯◯を取引先とみなす
    amount = re.search(r"([\d,]+)円", text).group(1)  # 「12,000円」の数字部分を取り出す
    return {"vendor": vendor, "amount": int(amount.replace(",", ""))}  # カンマを外して整数にする


def approval_route(amount: int) -> str:
    """承認の振り分け。分岐は多くても、ルールははっきりしている。"""
    if amount > 100_000:  # 10 万円を超えたら
        return "部長承認"
    if amount > 50_000:  # 5 万円を超えたら
        return "課長確認"
    return "自動承認"  # それ以下は人の確認なし


def process_invoice(text: str) -> str:
    """★ 手順は 1→2→3→4 で固定。どの請求書でも同じ道を通る。"""
    data = fake_llm_extract(text)  # 1. 抽出（LLM）
    if data["vendor"] not in VENDORS:  # 2. 検証（プログラム）。知らない取引先は止める
        return f"差し戻し: 未登録の取引先「{data['vendor']}」"
    route = approval_route(data["amount"])  # 3. 承認の振り分け（ルール）
    return f"登録: {data['vendor']} {data['amount']:,}円 → {route}"  # 4. 登録して結果を返す


for mail in [
    "青葉商事より 9月分の保守費用 38,500円 をご請求申し上げます",
    "北斗製作所より 部品代として 132,000円 を請求します",
    "南星物産より 120,000円 のご請求です",
]:
    print(process_invoice(mail))  # 3 通の請求メールを順に処理する
```

```text
登録: 青葉商事 38,500円 → 自動承認
登録: 北斗製作所 132,000円 → 部長承認
差し戻し: 未登録の取引先「南星物産」
```

`process_invoice` の中身が、そのまま Workflow の設計図になっている。LLM（ここでは偽物の `fake_llm_extract`）は、文面から項目を抜き出す 1 か所でしか使っていない。取引先の確認と承認の振り分けはプログラムが行うので、同じ請求書なら何度流しても同じ結果になる。

2 つ目の仕事は、顧客から「9 月の請求がいつもより高いのはなぜか」と聞かれて調べることだ。こちらは、**調べた結果によって次に見るべきものが変わる**。明細に見慣れない項目があれば作業記録を、基本料そのものが上がっていれば契約を見に行く。

```python title="billing_agent.py" caption="請求額が高い理由の調査。次にどの道具を使うかを、偽 LLM が直前の結果から決める"
INVOICES = {  # 顧客ごとの請求明細。月 → {項目: 金額}
    "A社": {"8月": {"基本料": 50_000}, "9月": {"基本料": 50_000, "追加作業": 30_000}},
    "B社": {"8月": {"基本料": 50_000}, "9月": {"基本料": 65_000}},
}
CONTRACTS = {"A社": "基本料 50,000円。改定なし", "B社": "9月から基本料を 65,000円に改定（6月に合意）"}
WORK_ORDERS = {"A社": "9/12 サーバー移設作業 30,000円（依頼者: 情報システム部）", "B社": "なし"}


def compare_lines(c):  # 道具 1: 先月と今月の明細を比べ、増えた項目を返す
    before, after = INVOICES[c]["8月"], INVOICES[c]["9月"]
    diffs = [f"{k} +{after[k] - before.get(k, 0):,}円" for k in after if after[k] != before.get(k)]
    return "増えた項目: " + "、".join(diffs)


TOOLS = {  # 道具の一覧。名前 → 実行する関数
    "compare_lines": compare_lines,
    "get_contract": lambda c: "契約: " + CONTRACTS[c],  # 道具 2: 契約内容を読む
    "get_work_orders": lambda c: "作業記録: " + WORK_ORDERS[c],  # 道具 3: 作業の記録を読む
}


def fake_llm(history: list) -> str:
    """★ 直前の結果を読んで、次の一手を決める（練習用の偽物）。本物は LLM が考える。"""
    last = history[-1]  # いちばん新しい結果
    if last.startswith("依頼"):  # まだ何も調べていない
        return "compare_lines"
    if "追加作業" in last:  # ★ 明細に見慣れない項目 → 作業記録を見に行く
        return "get_work_orders"
    if "基本料 +" in last:  # ★ 基本料そのものが上がった → 契約を見に行く
        return "get_contract"
    return "answer"  # 理由が分かったので答える


def run_agent(customer: str, max_steps: int = 5) -> None:
    history = [f"依頼: {customer} の 9月の請求が高い理由を調べて"]  # これまでの経過
    for _ in range(max_steps):  # ★ 最大 max_steps 回まで（止まらない事故を防ぐ）
        action = fake_llm(history)  # 次に何をするかは LLM が決める
        if action == "answer":
            print(f"  回答の根拠: {history[-1]}")  # 最後に見つけた根拠を答えに使う
            return
        result = TOOLS[action](customer)  # 選ばれた道具をプログラムが実行する
        print(f"  {action} → {result}")
        history.append(result)  # 結果を経過に足して、次の判断の材料にする
    print("  上限に達したので担当者に引き継ぐ")


for name in ["A社", "B社"]:
    print(name)
    run_agent(name)
```

```text
A社
  compare_lines → 増えた項目: 追加作業 +30,000円
  get_work_orders → 作業記録: 9/12 サーバー移設作業 30,000円（依頼者: 情報システム部）
  回答の根拠: 作業記録: 9/12 サーバー移設作業 30,000円（依頼者: 情報システム部）
B社
  compare_lines → 増えた項目: 基本料 +15,000円
  get_contract → 契約: 9月から基本料を 65,000円に改定（6月に合意）
  回答の根拠: 契約: 9月から基本料を 65,000円に改定（6月に合意）
```

同じ `run_agent` に同じ依頼を渡しているのに、A 社では作業記録を、B 社では契約を見に行った。道筋を決めているのは `run_agent` の行の並びではなく、ループの中で毎回呼ばれる `fake_llm` だ。これがエージェントの形である。

ここでは動きを確かめるために、偽 LLM の判断を if 文で書いた。本物の LLM は、こうした規則を書かなくても、結果の文面と道具の説明から次の一手を考える。だから想定していなかった理由（たとえば値引きの終了）にも対応できる。その代わり、同じ依頼でも毎回同じ道を通る保証はない。

| 見るところ | `invoice_workflow.py` | `billing_agent.py` |
|---|---|---|
| 次の処理を決めているもの | `process_invoice` の行の並び | ループの中の `fake_llm` |
| 処理の数 | いつも 4 つ | 調べてみるまで分からない |
| LLM の役割 | 1 工程の中で項目を抜き出す | 流れそのものを決める |
| 止める仕組み | 最後の行まで来たら終わる | `max_steps` の上限と「答える」判断 |

> [!WARNING] エージェントには必ず上限を付ける
> `run_agent` の `max_steps` は飾りではない。AI が「まだ足りない」と判断し続けると、ループは終わらず、費用と時間が増え続ける。上限に達したら人間に引き継ぐところまでを、最初から作っておく。制約の付け方は第 3 回で詳しく扱う。

## 二択ではなく「AI にどこまで任せるか」の段階で考える

Workflow かエージェントか、という二択で考えると、たいてい議論が行き詰まる。実際には、LLM の出力がプログラムの流れにどこまで影響するかで、いくつかの段階に分けられる。

Hugging Face のエージェント用ライブラリ smolagents の解説は、この「任せる度合い」を段階で示している。Andrew Ng も、ある仕組みが「エージェントかどうか」を論じるより、「どの程度エージェント的か」で考える方が役に立つと述べている。次の表は、smolagents の整理をもとに、この記事のコードに当てはめたものだ。

| 段階 | LLM の出力が決めるもの | 形を 1 行で書くと | この記事での例 |
|---|---|---|---|
| 0 | 何も決めない。結果を使うだけ | `data = llm_extract(text)` | 請求書の項目の抽出 |
| 1 | if / else のどちらへ進むか | `if llm_says_urgent(): fast_lane()` | 問い合わせを「急ぎ」と「通常」に分ける |
| 2 | どの道具を、どの引数で使うか | `TOOLS[llm_choice](args)` | 3 つの道具から 1 つを選ぶ |
| 3 | 続けるか、やめるか | `while llm_wants_more(): step()` | 請求額の理由の調査（`run_agent`） |
| 4 | 別のエージェントを起動するか | `if llm_delegates(): run_agent(sub)` | 調査を部下のエージェントに分担させる |

段階 0 と 1 は Workflow に入る。段階 2 で AI が道具を選び始め、段階 3 でループの継続を AI が決めると、はっきりエージェントになる。

段階を 1 つ上げるたびに、**事前に確かめるべき経路が増える**。段階 0 なら、抽出結果を確かめれば済む。段階 3 では、何回まわるか、どの順で道具を使うかが実行ごとに変わるので、テストで全部の経路を押さえることはできない。

> [!TIP] 迷ったら 1 段低い方から始める
> 段階 1 で済むなら、段階 3 にしない。Anthropic と OpenAI の構築ガイドは、どちらも「最も単純な構成から始め、足りないと分かってから複雑にする」ことを勧めている。段階は後から上げられるが、一度エージェントで作ったものを Workflow に戻すのは、作り直しに近い。

## 10 の判断基準で見分ける

設計の場で迷ったときは、次の 10 の観点で照らし合わせる。左の列に当てはまるものが多いほど Workflow、右の列が多いほどエージェントに向く。

| 判断基準 | Workflow が向いている | エージェントが向いている |
|---|---|---|
| 処理手順 | 事前に決められる | 状況によって変わる |
| 入力データ | 形式が一定 | 自然言語・非構造化文書など |
| 判断基準 | 明確なルールで表せる | 文脈や複数の要素を考え合わせる |
| 例外処理 | 例外のパターンを列挙できる | 想定外の状況が多い |
| 道具の選択 | 使う道具が決まっている | 状況に応じて選ぶ |
| 処理の繰り返し | 回数や条件が決まっている | 結果を見ながら追加で調べる |
| 再現性 | 同じ経路で処理したい | 状況に応じた柔軟さが要る |
| 速度・コスト | 低遅延・低コストを重視する | 推論のコストを許容できる |
| 品質管理 | テストケースやルールで確かめやすい | 判断の妥当性を評価する必要がある |
| リスク管理 | 厳密な実行順序や承認を求める | 判断の範囲を限定し、必要なら承認を求める |

このうち、見落とされやすいのが下の 3 行だ。

**速度・コスト。** エージェントは、結果を見るたびに LLM を呼ぶ。Anthropic は「エージェント的なシステムは、性能と引き換えに、待ち時間とコストを払うことが多い」と書いている。1 日に何万件も流す処理なら、1 件あたりの呼び出し回数がそのまま請求額に響く。

**品質管理。** Workflow は「この入力ならこの出力」というテストが書ける。エージェントは経路が毎回変わるので、同じ課題を何度も解かせて成功率を測るような評価が必要になる。

**リスク管理。** 決まった順番で承認を通すこと自体が目的の業務（経費精算の承認フローなど）では、順番を AI に選ばせる理由がない。

Google Cloud のアーキテクチャガイドも、文書の要約・翻訳・顧客の声の分類のように手順が決まった仕事なら、エージェントにしなくても、ほかの方法の方が効率的で安いと書いている。**LLM が必要なことと、エージェントが必要なことは別の話だ。**

## 「if 文が多い＝エージェント」ではない——ただし逆の場合もある

よくある誤解が、「条件分岐が多くて複雑だから、AI に判断させよう」というものだ。前のコードの `approval_route` を見てほしい。

```python title="invoice_workflow.py（抜粋）" caption="分岐が何十個に増えても、線がはっきりしている限りは Workflow でよい"
def approval_route(amount: int) -> str:
    if amount > 100_000:  # ★ 10 万円を超えたら部長。誰が見ても同じ判定になる
        return "部長承認"
    if amount > 50_000:  # 5 万円を超えたら課長
        return "課長確認"
    return "自動承認"  # それ以下は自動
```

こうした分岐が何十個あっても、**ルール自体がはっきりしている**なら Workflow のままでよい。むしろ、金額の線引きを AI に判断させると、同じ請求書が日によって違う承認先に回るおそれがある。監査で「なぜこの請求書は課長確認だったのか」と聞かれたとき、プログラムなら行を指させるが、AI の判断は指させない。

一方で、逆向きの場合もある。OpenAI の構築ガイドは、エージェントを検討すべき条件の 1 つに**「保守が難しいルール」**を挙げている。ルールが膨大で、更新するたびに費用がかかり、間違いも入り込みやすい場合だ。例として、取引先のセキュリティ審査が挙げられている。

2 つの話は矛盾しない。分けているのは、if 文の**数**ではなく**性質**だ。

| 分岐の性質 | 例 | 向く方式 |
|---|---|---|
| 線がはっきりしていて、数も管理できる | 金額で承認先を分ける、日付で締め日を決める | Workflow |
| 線ははっきりしているが、数が多い | 商品ごとの税率、地域ごとの送料 | Workflow（ルールを表やデータに出す） |
| 文脈で判断が変わり、書き切れない | 返金してよい事情か、契約書の条項が自社に不利か | LLM に判断させる |
| ルールが膨大で、改定のたびに書き直しが追いつかない | 取引先のセキュリティ質問票の審査 | LLM に判断させ、結論は人間が確かめる |

数が多いだけなら、if 文を表（設定ファイルやデータベース）に移せば保守できる。LLM に寄せる価値があるのは、**文脈を読まないと決められない判断**か、**書き下すこと自体が割に合わない判断**だ。

> [!IMPORTANT] 判断は AI に、線はプログラムに
> LLM に寄せる場合も、全部を任せる必要はない。「この返金依頼の理由は、規約のどの項目に当たるか」の分類だけを LLM にさせ、「返金額の上限」「承認が要る金額」はプログラムの if 文に残す。こうすると、柔軟さと監査のしやすさを両立できる。

## 「次に何をするか分からない」ならエージェント

if 文の数より確かな見分け方がある。**最初の時点で、次に何をするかを書き下せるか**だ。

「エラーの原因を調べて」という依頼を考える。ログを見る → DB を見る → メトリクス（CPU 使用率などの数値）を見る、と最初から決められるとは限らない。ログにタイムアウトが出ていれば外部のサービスを、遅い問い合わせが出ていれば DB を見に行く。何を見るかは、**前に見たものの中身で決まる**。

```flow caption="エージェント型の調査。何を見るかは、前に見たものの中身で決まる"
A([目標: 原因を特定する]) --> B(調べ方を選ぶ\nLLM):::hl
B --> C[道具を実行\nログ・DB・数値]
C --> D[結果を確かめる]
D --> E{原因に届いた?}
E -- いいえ --> B
E -- はい --> F([原因と根拠を報告])
```

Anthropic のガイドも、エージェントが向くのは「必要なステップ数を予測できず、決まった経路を書けない、開かれた問題」だとしている。前の節の `billing_agent.py` も、A 社と B 社で見に行く先が違った。手順を書き下そうとすると「場合による」が並ぶなら、それがエージェントを検討する合図だ。

> [!WARNING] 「場合による」が 2〜3 通りなら、まず分岐で書く
> 「場合による」の中身を列挙できて、2〜3 通りに収まるなら、段階 1（LLM に分岐先だけ選ばせる）で済むことが多い。エージェントにするのは、列挙しようとしても終わらないときだ。

## 工程ごとに点数を付けて判定する

判断基準を、そのまま使えるチェックリストにしておく。システム全体ではなく、**工程ごと**に答えるのがコツだ。

**処理の流れ**（はいが多いほど Workflow 向き）

- [ ] 処理の順序を事前に決められる
- [ ] 次に何をするかをルールで書ける
- [ ] 例外のパターンを事前に列挙できる
- [ ] 使う道具が決まっている
- [ ] 終わりの条件をはっきり書ける

**判断と探索**（はいが多いほどエージェント向き）

- [ ] 最初の時点で必要な処理が分からない
- [ ] 状況によって次の処理が変わる
- [ ] 複数の道具から選ぶ必要がある
- [ ] 結果を見て次の行動を決める必要がある
- [ ] 想定外のケースが多い
- [ ] 調べながら問題を解く必要がある

これを点数にして判定するコードが次だ。

```python title="judge.py" caption="工程ごとに「はい」の割合で判定し、全体の形を決める"
FLOW_QUESTIONS = [  # はいが多いほど Workflow 向き
    "処理の順序を事前に決められる",
    "次に何をするかをルールで書ける",
    "例外のパターンを事前に列挙できる",
    "使う道具が決まっている",
    "終わりの条件をはっきり書ける",
]
AGENT_QUESTIONS = [  # はいが多いほどエージェント向き
    "最初の時点で必要な処理が分からない",
    "状況によって次の処理が変わる",
    "複数の道具から選ぶ必要がある",
    "結果を見て次の行動を決める必要がある",
    "想定外のケースが多い",
    "調べながら問題を解く必要がある",
]


def judge_step(flow_yes: int, agent_yes: int) -> str:
    """★ 1 つの工程を判定する。はいの数を、それぞれの質問数で割って比べる。"""
    flow = flow_yes / len(FLOW_QUESTIONS)  # Workflow 側の「はい」の割合（0〜1）
    agent = agent_yes / len(AGENT_QUESTIONS)  # エージェント側の「はい」の割合（0〜1）
    if flow >= 0.6 and agent < 0.5:  # 固定できる、かつ探索はあまり要らない
        return "Workflow"
    if agent >= 0.5 and flow < 0.6:  # 探索が要る、かつ固定しにくい
        return "エージェント"
    return "要分解"  # ★ どちらとも言えない工程は、もっと細かく分けて判定し直す


def judge_system(steps: dict) -> str:
    """★ 工程ごとの判定を集めて、システム全体の形を決める。"""
    results = {name: judge_step(*answers) for name, answers in steps.items()}  # 工程ごとに判定
    for name, r in results.items():
        print(f"  {name}: {r}")
    kinds = set(results.values())  # 判定結果の種類（重複を除く）
    if kinds == {"Workflow"}:
        return "全体を Workflow で作る"
    if kinds == {"エージェント"}:
        return "全体をエージェントで作る"
    return "ハイブリッド: 工程ごとに分けて作る"


report = {"データ取得": (5, 0), "集計": (5, 0), "文章化": (4, 1), "PDF出力": (5, 0)}
incident = {"受付": (5, 0), "原因調査": (1, 6), "報告書作成": (4, 1), "通知": (5, 0)}
for title, steps in [("定型レポート", report), ("障害調査", incident)]:
    print(title)
    print("  →", judge_system(steps))
```

```text
定型レポート
  データ取得: Workflow
  集計: Workflow
  文章化: Workflow
  PDF出力: Workflow
  → 全体を Workflow で作る
障害調査
  受付: Workflow
  原因調査: エージェント
  報告書作成: Workflow
  通知: Workflow
  → ハイブリッド: 工程ごとに分けて作る
```

`report` や `incident` の `(5, 0)` は、その工程について「処理の流れ」側で 5 つ、「判断と探索」側で 0 つ「はい」と答えた、という意味だ。

`judge_step` は、2 つの割合を見て工程を 3 つに分ける。どちらとも言えない工程は「要分解」とし、さらに細かい工程に分けて答え直す。たいていは、細かく分けると Workflow の部分とエージェントの部分に分かれる。

`judge_system` が、この記事でいちばん伝えたいことを表している。障害調査は「エージェント向きの仕事」と言われがちだが、工程に分けると、エージェントが要るのは原因調査だけだった。受付・報告書作成・通知は、手順が決まった Workflow だ。

> [!NOTE] 0.6・0.5 という線は目安
> 判定の線（0.6 と 0.5）は、この記事で決めた目安で、どこかの規格に基づくものではない。大事なのは点数そのものより、**工程ごとに答えると、どこにだけ AI の判断が要るかが見える**ことだ。線はチームで使いながら調整すればよい。

## 見分けるときの要点

| 問い | 答えが「はい」なら |
|---|---|
| 次に何をするかを、最初に書き下せるか | Workflow |
| 分岐は多いが、線ははっきりしているか | Workflow（多ければ表に出す） |
| 判断に文脈が要り、ルールを書き切れないか | その判断だけ LLM に任せ、線はプログラムに残す |
| 結果を見るまで次の手が決まらないか | エージェント |
| 工程に分けると、答えが工程ごとに違うか | ハイブリッド |

- [ ] 「AI を使うか」ではなく「流れを誰が決めるか」で考えた
- [ ] 任せる度合いを 5 段階で考え、いちばん低い段階から試した
- [ ] if 文の数ではなく、性質（線がはっきりしているか）で判断した
- [ ] システム全体ではなく、工程ごとに判定した
- [ ] エージェントにする工程には、最初から上限と引き継ぎ先を決めた

次回は、レポート作成・請求書処理・データパイプライン・障害調査・問い合わせ対応など 8 つの業務を取り上げ、それぞれでどちらを選ぶか、Workflow の中のどこで AI を使うかを、図とコードで見ていく。
