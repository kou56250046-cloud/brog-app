「AIエージェントを作りたい」と言っても、LLM に API をつないだだけのものから、何体もの AI が分担して働く仕組みまで、指している範囲は広い。どこまで作れば「業務で使える」のか分からないまま、フレームワークの機能一覧を眺めて迷うことも多い。

この連載では、AIエージェントを **16 の部品**に分解し、**3 つの段階**のどこでどの部品が必要になるかを整理する。第 1 話のこの記事では、全体の地図を示してから、最初の段階の部品（LLM・Tool・Tool 選択・簡単な RAG）を実際に動かす。

> [!TIP] この記事で分かること
> - AIエージェントを構成する 16 の部品と、それぞれの役割
> - シンプル・実用的・高度の 3 段階で、部品がどう増えていくか
> - LLM がデータベースを直接触らず、Tool を通す理由
> - ツールが増えたときに選択を間違えないための「候補の絞り込み」
> - 社内規程を検索して答える、最も簡単な RAG の作り方

エージェントの心臓部である「ループ」の仕組みは、別の記事「[AIエージェントは「賢さ」より「設計」で決まる](2026-09-29-ai-agent-design-fundamentals.html)」で詳しく書いた。この連載はその続きとして、ループの周りに付ける部品を 1 つずつ見ていく。内容は特定の AI サービスに依存しない。

## コードの読み方

コードはすべて Python で書き、外部のライブラリを使わずに動くようにした。**本物の LLM の代わりに、決まった判断をする練習用の偽物**を使うので、API キーがなくても手元で動きを確かめられる。

プログラミングをしない人でも流れを追えるように、ほぼ全行に日本語の説明を付けた。特に大事な行には `★` を付けてある。

| 書き方 | 意味 |
|---|---|
| `# 〜` | 説明文（コメント）。プログラムとしては無視される |
| `def 名前(引数):` | 「関数」の定義。決まった手順に名前を付けたもの。**引数**はその手順に渡す材料 |
| `return 値` | 関数の結果として、その値を返して終わる |
| `if 条件:` | 条件に合うときだけ、下の字下げされた行を実行する |
| `for x in 並び:` | 並びの中身を 1 つずつ `x` に入れて繰り返す |
| `[a, b]` / `{"名前": 値}` | リスト（順番のある入れ物）/ 辞書（名前と値の組の入れ物） |
| `f"...{名前}..."` | `{}` の中に変数の値を埋め込んだ文字列 |

## 16 の部品を 1 枚の地図にする

AIエージェントを部品に分けると、次の 16 個になる。役割ごとに 7 つのまとまりに分けておくと覚えやすい。

```flow caption="AIエージェントの部品を役割でまとめた地図。中心の LLM から外側へ部品が増えていく"
A([ユーザーの依頼]) --> B(LLM\n判断する頭脳):::hl
B --> C[手足\nTool・Tool選択\n複数Tool]
B --> D[進め方\n複数ステップ\nPlanning・State管理]
B --> E[知識\nMemory・RAG]
C --> F[失敗への備え\nエラー処理・リトライ\nログ・監視]
D --> F
E --> F
F --> G[守り\n権限管理・Human承認\nセキュリティ]
G --> H([分担\n複数Agent])
```

| # | 部品 | 一言でいうと | 連載で扱う回 |
|---|---|---|---|
| 1 | LLM | 依頼を理解し、次に何をするか決める頭脳 | 第 1 話 |
| 2 | Tool | SQL・API・Web 検索など、外の機能を使う手足 | 第 1 話 |
| 3 | Tool 選択 | 複数の Tool から「今どれを使うか」を決める | 第 1 話 |
| 4 | 複数 Tool | 1 つの仕事で Tool を次々に使う | 第 2 話 |
| 5 | 複数ステップ | 1 回で答えず、処理を順番に重ねる | 第 2 話 |
| 6 | Planning | 仕事を小さなタスクに分け、順番を決める | 第 2 話 |
| 7 | State 管理 | どこまで終わったかを覚えておく | 第 2 話 |
| 8 | Memory | 好み・過去の会話・過去の結果を後で使う | 第 3 話 |
| 9 | RAG | 社内文書を検索して LLM に渡す | 第 1・3 話 |
| 10 | エラー処理 | Tool や API の失敗を適切に扱う | 第 4 話 |
| 11 | リトライ | 一時的な失敗を条件付きでやり直す | 第 4 話 |
| 12 | 権限管理 | 誰が・どの AI が・どのデータを使えるか決める | 第 5 話 |
| 13 | Human 承認 | 重要な操作の前に人間の確認を挟む | 第 5 話 |
| 14 | ログ・監視 | 何をしたか・いくらかかったかを記録する | 第 4 話 |
| 15 | 複数 Agent | 専門の役割を持つ AI を協調させる | 第 6 話 |
| 16 | セキュリティ | 情報漏洩や不正操作を防ぐ | 第 5 話 |

この 16 個は、どれか 1 つの論文や規格が定めた一覧ではない。ただ、研究者の Lilian Weng は 2023 年の解説で、エージェントを「LLM ＋ 計画 ＋ 記憶 ＋ ツールの使用」と表した。守りの部品は、OWASP（Web のセキュリティを扱う国際的なコミュニティ）がエージェントの主要なリスクとして挙げている。一覧の中身は、こうした整理とおおむね重なっている。

## 3 段階は「何が起きたら困るか」で決まる

16 個を最初から全部作る必要はない。部品は、エージェントに任せる仕事が大きくなるにつれて**必要に迫られて増えていく**。この連載では、それを 3 段階で整理する。

| 段階 | 部品 | 任せる仕事の例 | 増えた部品が防ぐこと |
|---|---|---|---|
| ① シンプル | LLM・Tool・Tool 選択・少数のステップ・簡単な RAG | 「青葉商事の売上は？」に答える | ―（最小構成） |
| ② 実用的 | ①＋複数 Tool・複数ステップ・Planning・State・Memory・RAG・エラー処理・リトライ・権限・Human 承認・ログ・セキュリティ | 顧客と売上を集めて比較し、レポートを作ってメールの下書きまで用意する | 途中で失敗して最初からやり直す、見てはいけないデータを見る、勝手に送信する |
| ③ 高度 | ②のすべて＋複数 Agent・高度な Planning / State / Memory・高度な権限とセキュリティ・大規模な監視と運用 | 部署をまたぐ調査を、複数の AI が分担して数時間かけて進める | 1 体では文脈に収まらない、何十人が同時に使う、どこで間違えたか追えない |

段階が上がるほど、**LLM の賢さより、周りの仕組みの比重が大きくなる**。段階②で増える部品のほとんどは、失敗・権限・記録を扱うものだ。

Anthropic や OpenAI の構築ガイドも、**最も単純な構成から始め、必要になったときだけ複雑にする**ことを勧めている。段階を上げるのは、下の段階で困ったことが起きてからでいい。

```flow caption="段階を上げる判断。困りごとが起きてから部品を足す"
A([段階①で動かす]) --> B{途中で失敗して\n困ったことがある?}
B -- はい --> C[段階②の部品を足す\n第2〜5話]:::hl
B -- いいえ --> D([①のまま使う])
C --> E{1体の文脈に\n収まらない?}
E -- はい --> F[段階③の部品を足す\n第6話]
E -- いいえ --> G([②のまま使う])
```

## 題材：営業支援エージェント

連載を通して、同じ題材を少しずつ育てていく。**営業担当を手伝うエージェント**だ。扱うデータと操作は次の 3 種類にする。

| データ・操作 | 中身 | 使う Tool |
|---|---|---|
| 顧客データベース | 顧客名・担当者・今期の売上 | SQL で引く `get_customer` |
| 社内規程 | 経費・見積・情報管理のルール | 規程を検索する `search_rules`（RAG） |
| メール | 顧客への連絡 | 下書きを作る `draft_email` |

この記事では段階①まで作る。質問に対して Tool を 1 つ選び、1 回使って答えるだけのエージェントだ。

```flow caption="段階①のエージェント。Tool を 1 回使って答える"
A([ユーザーの質問]) --> B[候補の Tool を絞る]
B --> C(LLM が Tool を選ぶ):::hl
C --> D[Tool を実行]
D --> E(結果を LLM に渡す)
E --> F([回答])
```

## LLM は判断だけ、手を動かすのは Tool

LLM は、文章を受け取って文章を返す部品だ。データベースに接続したり、メールを送ったりする機能は、LLM 自身には無い。

そこで、外の世界に働きかける処理は **Tool（ツール）** としてプログラム側に用意する。LLM は「どの Tool を、どんな引数で使いたいか」を返すだけで、実行するのはプログラムだ。

| 役割 | 担当 | 例 |
|---|---|---|
| 何をするか決める | LLM | 「`get_customer` を、顧客名「青葉商事」で使いたい」 |
| 実際に実行する | プログラム（Tool） | SQL を投げて、1 件を取り出す |
| 結果を文章にする | LLM | 「青葉商事の今期売上は 1,200 万円です」 |

この「LLM が Tool の使用を頼み、プログラムが実行する」仕組みは、サービスによって呼び名が違う。OpenAI と Google は Function calling、Anthropic は Tool use と呼ぶが、中身は同じだ。

### なぜ LLM に SQL を直接書かせないのか

LLM に SQL を自由に書かせて実行する作り方もできる。ただし、その場合は LLM が書いた SQL がそのまま DB で動く。削除の命令や、見てはいけない表を読む命令でもそのまま動いてしまう。

そこで、**SQL の形はプログラム側で固定し、LLM には中に入れる値だけを決めさせる**。次のコードがその例だ。

```python title="customer_db.py" caption="顧客 DB を引く Tool。SQL の形は固定し、LLM が決めるのは顧客名だけ"
import sqlite3  # Python に最初から入っている小さなデータベース


def open_db():
    """練習用の顧客データベースをメモリ上に作る（本番なら社内の DB につなぐ）。"""
    con = sqlite3.connect(":memory:")  # ファイルを作らず、メモリの中だけに DB を作る
    con.execute("CREATE TABLE customers (id TEXT, name TEXT, owner TEXT, sales INTEGER)")  # 表を作る
    con.executemany(  # 顧客を 2 件入れる。sales は今期の売上（万円）
        "INSERT INTO customers VALUES (?, ?, ?, ?)",
        [("C001", "青葉商事", "sato", 1200), ("C002", "北斗製作所", "suzuki", 800)],
    )
    return con


DB = open_db()  # 起動時に 1 回だけ作る


def get_customer(name: str) -> str:
    """★ 顧客名を受け取り、決まった SQL で 1 件だけ引く。LLM が書くのは「顧客名」だけ。"""
    row = DB.execute(
        "SELECT id, name, owner, sales FROM customers WHERE name = ?",  # ★ SQL の形は固定
        (name,),  # ? の位置に顧客名を安全に差し込む（SQL を書き換えられないようにする仕組み）
    ).fetchone()  # 最初の 1 件だけ取り出す。無ければ None（何も無い、の意味）
    if row is None:  # 見つからなかったとき
        return f"顧客「{name}」は見つかりません。正式な社名で指定してください。"  # 次にどうすればいいかまで返す
    return f"{row[1]}（ID {row[0]}） 担当: {row[2]} / 今期売上: {row[3]} 万円"
```

`get_customer` は、顧客名を受け取って 1 件だけ返す Tool だ。ポイントは 2 つある。

**1. SQL の形を固定している。** `WHERE name = ?` の `?` に顧客名が入るだけなので、LLM がどんな文字を渡しても、別の表を読んだり行を消したりする命令にはならない。この `?` の書き方を**プレースホルダー**と呼び、SQL インジェクション（入力に命令を紛れ込ませる攻撃）を防ぐ基本の書き方だ。

**2. 見つからないときに次の手を返している。** 「見つかりません」だけでなく「正式な社名で指定してください」と返すと、LLM はそれを読んで引数を直せる。エラーの返し方は第 4 話で詳しく扱う。

> [!WARNING] 自由な SQL を許すなら、読み取り専用の接続にする
> 分析用途などで LLM に SQL を書かせたい場合もある。そのときは、書き込み権限のない DB ユーザーで接続し、読める表も絞っておく。LLM への指示文で「削除しないで」と頼んでも、それは守られる保証のないお願いでしかない。

## Tool 選択：候補が多いほど間違える

Tool が 3 つなら、LLM は説明文を読んで正しいものを選べる。ところが Tool が数十個に増えると、選び間違いが目立ってくる。

2026 年に公開された研究では、LLM に見せる Tool の数と選択の正確さの関係を調べている。Tool が増えると、似た説明の Tool に迷いが分散し、存在しない Tool 名を作ったり、別の Tool の引数を混ぜたりする。この研究では、**先に検索で候補を絞ってから LLM に選ばせる**方が、全部を見せるより正確だった。

何個から精度が落ちるかは、報告によって 10〜15 個、15〜20 個とばらつきがある。確実に言えるのは、**増えるほど落ちるので、見せる数を絞る仕組みを持っておく**ということだ。

| 対策 | やり方 | 向いている場面 |
|---|---|---|
| 説明文を具体的にする | 「何に使うか」「何が返るか」を書く | Tool が数個のとき。まずここから |
| 候補を絞る | 質問と説明文の近さで上位だけ見せる | Tool が十数個を超えたとき |
| エージェントを分ける | 「顧客担当」「規程担当」のように Tool の組で分ける | 分野がはっきり分かれるとき（第 6 話） |

次のコードは、Tool の一覧と、質問に近い Tool だけを残す絞り込みだ。

```python title="tools.py" caption="Tool の一覧と、質問に近い Tool に候補を絞る関数"
from customer_db import get_customer  # 顧客 DB を引くツール
from rules_rag import bigrams, search_rules  # 規程を検索するツールと、2 文字に分ける道具


def draft_email(body: str) -> str:
    """メールの下書きを作るだけで、送信はしない（送信は人間が確認してから）。"""
    return f"下書きを保存しました: {body[:30]}…"  # [:30] は先頭 30 文字だけ


# ★ ツールの一覧。LLM が読むのは description（説明）だけなので、何に使うかを具体的に書く
TOOLS = {
    "get_customer": {"fn": get_customer, "arg": "name",
                     "description": "顧客名から、その顧客の担当者と今期の売上を調べる"},
    "search_rules": {"fn": search_rules, "arg": "query",
                     "description": "社内規程を調べる。接待費や経費の上限、見積の期限など"},
    "draft_email": {"fn": draft_email, "arg": "body",
                    "description": "顧客へのメールの下書きを作る（送信はしない）"},
}


def narrow_tools(question: str, k: int = 2) -> list[str]:
    """★ 質問と説明文が似ているツールを k 個に絞る。LLM に見せる候補を減らすため。"""
    q = bigrams(question)  # 質問を 2 文字の組に分ける
    ranked = sorted(TOOLS, key=lambda name: len(q & bigrams(TOOLS[name]["description"])), reverse=True)
    return ranked[:k]  # 似ている順に k 個
```

`TOOLS` は、Tool の名前・実体・引数名・説明文を並べた辞書だ。本物の LLM に渡すときは、この説明文を JSON Schema（引数の形を表す共通の書き方）に書き直して渡す。

`narrow_tools` は、質問と説明文で共通する「2 文字の組」の数を数え、多い順に `k` 個を残す。本番では、文章の意味を数値の並びにした**埋め込みベクトル**で近さを測ることが多い。ただ、やっていることは同じで、**LLM に見せる前に候補を減らしている**。

実行すると、次のように絞り込まれる。

| 質問 | 残った候補（近い順） |
|---|---|
| 青葉商事の売上は？ | `get_customer`, `search_rules` |
| 接待費の上限は？ | `search_rules`, `get_customer` |
| 見積の期限をメールで伝えたい | `search_rules`, `draft_email` |

3 つ目の質問では、規程を調べる Tool とメールの Tool が残った。「期限を調べてからメールを書く」という 2 段の仕事になるので、実際には Tool を 2 つ続けて使う必要がある。これが段階②の「複数 Tool・複数ステップ」で、第 2 話で扱う。

> [!NOTE] 説明文は LLM への指示文でもある
> LLM は Tool の中身を見られない。見えるのは名前と説明文と引数の形だけだ。「顧客情報を取得」より「顧客名から、その顧客の担当者と今期の売上を調べる」の方が、どんな質問のときに使うべきかが伝わる。

## 簡単な RAG：規程を検索して LLM に渡す

LLM は、学習したときのデータに含まれていない情報を知らない。自社の経費規程も、先月変わった見積のルールも知らない。

**RAG**（Retrieval-Augmented Generation、検索で補強した生成）は、質問に関係する文書を先に検索し、その文章を LLM に渡してから答えさせる仕組みだ。LLM に知識を覚えさせるのではなく、**答えるたびに資料を手元に置いてあげる**方式と考えるとよい。

| 方式 | 何をするか | 情報が変わったとき |
|---|---|---|
| LLM の知識だけで答える | 学習済みの知識で答える | 反映されない |
| RAG | 検索した文書を渡して答えさせる | 文書を差し替えればすぐ反映される |

次のコードは、最も簡単な RAG の「検索」部分だ。

```python title="rules_rag.py" caption="社内規程を、質問と共通する文字の組の多さで検索する"
# 社内規程。本番ならファイルや文書管理システムから読み込む
RULES = {
    "経費規程 第3条": "接待費は1人あたり5,000円までとし、超える場合は事前に部長の承認を得る。",
    "営業規程 第7条": "見積書の有効期限は発行日から30日とする。",
    "情報管理規程 第2条": "顧客の個人情報をメールで社外へ送ってはならない。共有リンクを使う。",
}


def bigrams(text: str) -> set[str]:
    """文章を「2 文字ずつの組」に分ける。例: "接待費" → {"接待", "待費"}"""
    return {text[i : i + 2] for i in range(len(text) - 1)}  # set は重複しない入れ物


def search_rules(query: str, k: int = 1) -> str:
    """★ 質問と共通する 2 文字の組が多い規程から順に k 件返す（ごく簡単な検索）。"""
    q = bigrams(query)  # 質問を 2 文字の組に分ける
    ranked = sorted(  # 規程を「似ている順」に並べ替える
        RULES.items(),
        key=lambda item: len(q & bigrams(item[1])),  # & は「両方にある組」。その数で比べる
        reverse=True,  # 多い順（大きい順）にする
    )
    # ★ 出典（どの規程の何条か）を付けて返す。LLM が根拠を示せるようにするため
    return "\n".join(f"[{title}] {body}" for title, body in ranked[:k])
```

`search_rules` は、質問を 2 文字ずつの組に分け、規程の本文と共通する組が多い順に並べる。「接待費の上限は？」なら、「接待」「待費」「上限」などが一致する経費規程 第 3 条が先頭に来る。

大事なのは最後の行で、**検索結果に出典（何規程の何条か）を付けて返している**。LLM はこれを読んで「経費規程 第 3 条によると…」と根拠付きで答えられる。利用者も、答えが本当に規程に書いてあるかを確かめられる。

> [!WARNING] 簡単な RAG が通用するのは文書が少ないうち
> 文字の一致だけの検索は、言い換え（「接待費」と「会食代」）に弱い。文書が数百件を超える、規程の版が複数ある、部署によって見せてよい文書が違う、という段階になると作り直しが必要になる。文書の分け方・版の扱い・権限は第 3 話で扱う。

## 段階①のエージェントを組み立てる

ここまでの部品をつなぐ。流れは「候補を絞る → LLM が選ぶ → Tool を実行する → 結果を返す」の 4 つだ。

```python title="simple_agent.py" caption="段階①のエージェント。Tool を 1 回だけ使って答える"
from tools import TOOLS, narrow_tools  # ツールの一覧と、候補を絞る関数


def fake_llm_choose(question: str, candidates: list[str]) -> dict:
    """練習用の偽 LLM。本物は説明文を読んで選ぶが、ここでは言葉の手がかりで真似る。"""
    if "get_customer" in candidates and ("売上" in question or "担当" in question):
        name = question.split("の")[0]  # 「青葉商事の売上は？」→「青葉商事」を取り出す
        return {"tool": "get_customer", "arg": name}  # ★ 「このツールをこの引数で」と返す
    if "search_rules" in candidates:
        return {"tool": "search_rules", "arg": question}
    return {"tool": None}  # 使うツールが無い


def run_simple_agent(question: str) -> str:
    """段階①のエージェント。ツールを 1 回だけ使って答える。"""
    candidates = narrow_tools(question)  # ① 候補のツールを絞る
    choice = fake_llm_choose(question, candidates)  # ② LLM がツールを選ぶ
    if choice["tool"] is None:  # 使えるツールが無ければ、正直にそう答える
        return "手元のツールでは答えられません。"
    tool = TOOLS[choice["tool"]]  # 選ばれたツールの中身を取り出す
    result = tool["fn"](choice["arg"])  # ③ ★ ツールを実行する（LLM ではなくプログラムが動かす）
    # ④ 本物ならここで結果を LLM に渡し、文章に整えてもらう。偽物では結果をそのまま添える
    return f"（{choice['tool']} を使用）{result}"


if __name__ == "__main__":  # このファイルを直接実行したときだけ動く
    for q in ["青葉商事の売上は？", "接待費の上限は？", "東西物産の担当は？"]:
        print(q, "→", run_simple_agent(q))  # 質問ごとに答えを表示する
```

`fake_llm_choose` は練習用の偽 LLM で、本物なら LLM の API を呼ぶ部分だ。本物の LLM は Tool の説明文を読んで選ぶが、偽物は「売上」「担当」という言葉があれば顧客 DB、なければ規程検索、という決め打ちで真似している。

`run_simple_agent` の ★ の行が、この記事でいちばん伝えたいところだ。**LLM は「どれを使うか」を返すだけで、Tool を実行するのはプログラム**だ。実行する前にプログラム側で検査を挟めるので、第 5 話の権限管理や承認は、この場所に足していくことになる。

実行結果は次のとおり。

```bash title="実行結果"
$ python simple_agent.py
青葉商事の売上は？ → （get_customer を使用）青葉商事（ID C001） 担当: sato / 今期売上: 1200 万円
接待費の上限は？ → （search_rules を使用）[経費規程 第3条] 接待費は1人あたり5,000円までとし、超える場合は事前に部長の承認を得る。
東西物産の担当は？ → （get_customer を使用）顧客「東西物産」は見つかりません。正式な社名で指定してください。
```

3 つ目の質問では、存在しない顧客を聞いている。エージェントは作り話をせず、「見つからない」と次の手を返した。答えを LLM の知識ではなく Tool の結果から作っているので、**知らないことを知らないと言える**。

### 段階①で足りなくなる 3 つの場面

このエージェントは 1 回の質問に 1 回の Tool で答えるだけだ。次のような依頼が来ると、すぐに足りなくなる。

| 依頼 | 足りないもの | 扱う回 |
|---|---|---|
| 「青葉商事と北斗製作所の売上を比べてレポートにして」 | 複数 Tool・複数ステップ・Planning・State | 第 2 話 |
| 「先週話した件の続きをお願い」 | Memory | 第 3 話 |
| 「DB が落ちていたらどうなる？」 | エラー処理・リトライ・ログ | 第 4 話 |
| 「他の営業担当の顧客も見られてしまう」 | 権限管理・Human 承認・セキュリティ | 第 5 話 |

## 自分のエージェントはどの段階か

最後に、作ろうとしているエージェントが 3 段階のどこにいるかを判定する表を置く。**「はい」が 1 つでもあれば、その段階の部品が必要になる**。

| 問い | 「はい」なら |
|---|---|
| 1 回の依頼で、Tool を 2 回以上続けて使う必要があるか | 段階②（第 2 話） |
| 処理が数分以上かかり、途中で止まったら困るか | 段階②（第 2・4 話） |
| 前回の会話や、利用者の好みを覚えておく必要があるか | 段階②（第 3 話） |
| 利用者によって見てよいデータが違うか | 段階②（第 3・5 話） |
| メール送信・登録・支払いなど、取り消しにくい操作をするか | 段階②（第 5 話） |
| 1 体の LLM の文脈（一度に読める量）に仕事が収まらないか | 段階③（第 6 話） |
| 多くの人が同時に使い、コストや失敗を継続的に追う必要があるか | 段階③（第 4・6 話） |

どれにも当てはまらないなら、段階①で十分だ。部品を増やすほど、作る手間とテストの手間、そして LLM の呼び出し回数（＝コスト）が増える。
