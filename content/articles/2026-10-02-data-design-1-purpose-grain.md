売上の数字が、部署ごとに違う。営業は 3 月を 3 万円と言い、経理は 2 万円と言う。どちらも同じ注文データから集計しているのに、合わない。

## コードの読み方

コードは Python と SQL で書き、ほぼ全行に日本語の説明を付けた。特に大事な行には `★` を付けてある。Python に最初から入っている `sqlite3`（ファイル 1 つで動く小さなデータベース）だけを使うので、追加のインストールは要らない。記事のコードを上から順に貼り付けていけば、同じ結果が出る。

| 書き方 | 意味 |
|---|---|
| `# 〜` / `-- 〜` | Python / SQL の説明文（コメント）。プログラムとしては無視される |
| `def 名前(引数):` | 「関数」の定義。決まった手順に名前を付けたもの |
| `for x in 並び:` | 並びの中身を 1 つずつ取り出して繰り返す |
| `[a, b]` / `{"名前": 値}` | リスト（順番のある入れ物） / 辞書（名前と値の組の入れ物） |
| `"""…"""` | 複数行の文字列。この記事では中に SQL を書いている |
| `f"…{x}…"` | 文字列の中に変数 `x` の値を埋め込む書き方 |

**SQL** は、データベースに命令する言語だ。`SELECT 列 FROM 表 WHERE 条件 GROUP BY 列` は「表から、条件に合う行を、列の値ごとにまとめて取り出す」と読めばよい。

## 全体マップ：テーブルを作る前に決める 4 つのこと

テーブル定義（`CREATE TABLE`）を書くのは最後だ。その前に、使い道・業務・意味・粒度の順に決めていく。

```flow caption="この記事の流れ。上の決定が下の設計を縛る"
A([誰が何を決めるためのデータか]) --> B[業務を調べる\n流れ・用語・タイミング・責任者]
B --> C[意味を定義する\n単位・集計方法・更新頻度]
C --> D[粒度を宣言する\n1 行 = 何か]:::hl
D --> E[粒度を検査で守る]
E --> F([テーブルを作る])
```

## 「誰が何を決めるためのデータか」から逆算する

データ設計でいちばん多い失敗は、**手元にあるデータをどう並べるか**から始めることだ。業務システムの表をそのまま写し、「あとで何にでも使えるように」と列を全部持ってくる。すると誰の質問にも直接は答えられない表ができる。

先に決めるのは、次の 4 つだ。

1. **何のため**：どんな意思決定・業務に使うか（例：来月の仕入れ量を決める）
2. **誰が**：使う人・システムは誰か（経営、現場、分析者、機械学習モデル、AI エージェント）
3. **何を見て決めるか**：その判断に要る数字と切り口（例：商品別・週別の販売数）
4. **これからの使い道**：半年後に増えそうな用途（例：需要予測の学習データにする）

使い道によって、データに求められる性質は大きく変わる。

| 使い道 | 求められる粒度 | 鮮度 | 履歴 | 特に要るもの |
|---|---|---|---|---|
| BI・定型レポート | 日・月などに集計済みでよい | 日次が多い | 前年比が出せる程度 | 指標の定義が 1 つに決まっていること |
| 分析（アドホック） | 最も細かい単位 | 日次〜週次 | 長期間 | 切り口を自由に変えられる構造 |
| 機械学習 | 予測したい単位（顧客×月など） | 学習時と推論時で揃う | **その時点で分かっていた値** | 未来の情報が混ざらないこと |
| RAG・AI エージェント | 質問に答えられる単位 | 用途による | 版と有効期間 | 列・文書の説明文、権限 |

表の「機械学習」の行が特に落とし穴になる。顧客の「現在の住所」だけを持っていると、3 年前の購買を予測する学習データに、3 年後に分かった住所が混ざる。履歴の持ち方は[第 5 回](2026-10-02-data-design-5-history-scd.html)で扱う。

> [!WARNING] 「とりあえず全部取っておく」の落とし穴
> 生データを残しておくこと自体は正しい（[第 6 回](2026-10-02-data-design-6-architecture.html)の Raw 層）。問題は、生データを**そのまま利用者に見せる**ことだ。使い道を決めずに作った表は、列の意味を利用者ごとに推測させることになり、同じ「売上」から違う数字が出る。

## 業務を知らずに作ったテーブルは、業務と食い違う

テーブルは業務の写しだ。業務を知らずに作ると、写し間違える。調べるのは次の 6 つだ。

| 調べること | 問いの例 | 分からないと起きること |
|---|---|---|
| 業務プロセス | 注文から入金まで、どんな段階を経るか | 「キャンセル」がどの段階で起きるか分からず、集計から外せない |
| 業務ルール | 送料は注文ごとか、商品ごとか | 送料を商品の数だけ数えてしまう |
| 業務上の用語 | 「売上」は受注・出荷・請求のどの時点か | 部署ごとに違う数字が出る |
| 発生タイミング | 行はいつ作られるか | 夜間に作られる行を、昼の集計で取りこぼす |
| 更新タイミング | 作られた行は後から変わるか | 確定済みと思った金額が翌月に書き換わる |
| データの責任者 | 間違いを誰に直してもらうか | 誤りを見つけても直す人がいない |

業務の流れは、図にして関係者と確かめるのが早い。

```flow caption="通販の注文の流れ。どの段階で行が作られ、どの値が変わるかを書き込む"
direction LR
A([受注\n注文日が決まる]) --> B[出荷\n出荷日が決まる]
B --> C[請求\n請求日・金額が確定]
C --> D([入金\n入金日が決まる])
A -.-> X[キャンセル]:::muted
B -.-> Y[返品]:::muted
```

この流れを知っていれば、「売上を月ごとに出して」と言われたときに、**どの日付で月を決めるのか**を聞き返せる。実際に、同じ 3 件の注文でも日付の選び方で結果が変わる。

```python title="sales_by_date.py" caption="同じ注文でも、どの日付で月を決めるかで月別売上が変わる" {9,19}
import sqlite3  # Python に最初から入っている小さなデータベース

con = sqlite3.connect(":memory:")  # メモリの上に使い捨てのデータベースを作る
con.executescript("""
-- 注文の表。1 行 = 注文 1 件
CREATE TABLE orders (
  order_id     INTEGER PRIMARY KEY,  -- 注文番号
  customer_id  INTEGER,              -- 注文した顧客の番号
  ordered_on   TEXT, shipped_on TEXT, invoiced_on TEXT,  -- ★ 日付が 3 種類ある
  amount       INTEGER,              -- 商品代金（円・税抜）
  shipping_fee INTEGER               -- 送料（円・税抜）。注文 1 件につき 1 回
);
INSERT INTO orders VALUES
  (1, 1, '2026-03-28', '2026-04-02', '2026-04-30', 10000, 500),
  (2, 2, '2026-03-30', '2026-03-31', '2026-04-30', 20000, 500),
  (3, 1, '2026-04-05', '2026-04-06', '2026-04-30', 15000,   0);
""")

for col in ["ordered_on", "shipped_on", "invoiced_on"]:  # ★ 3 種類の日付で順に集計する
    rows = con.execute(f"""
        SELECT substr({col}, 1, 7) AS month,  -- 日付の先頭 7 文字（例: 2026-03）を月とする
               SUM(amount)                    -- その月の商品代金を合計する
        FROM orders GROUP BY month ORDER BY month
    """).fetchall()                          # 結果を全部受け取る
    print(col, rows)                         # どの日付で集計したかと結果を表示
```

実行結果は次のとおりだ。

```text
ordered_on [('2026-03', 30000), ('2026-04', 15000)]
shipped_on [('2026-03', 20000), ('2026-04', 25000)]
invoiced_on [('2026-04', 45000)]
```

9 行目のように日付が 3 種類あると、19 行目のループで集計の基準を変えるだけで、3 月の売上は 3 万円・2 万円・0 円と変わる。どれも SQL としては正しい。冒頭の「営業は 3 万円、経理は 2 万円」は、受注日で数えるか出荷日で数えるかの違いだった、ということになる。

> [!IMPORTANT]
> どの日付を使うかは、データの担当者ではなく**業務**が決めることだ。会計上の売上計上の基準は会社の会計方針で決まっている。設計者の仕事は、それを聞き出して定義に書き、全員が同じ定義を使える形にすることだ。

## 値と意味をセットで持つ：データ定義書

前の例で分かったとおり、`amount` という列名だけでは、税込みか税抜きか、送料を含むか、いつ確定するかが分からない。値には、**意味を書いた定義**を必ず添える。列ごとに書く項目は次のとおりだ。

| 項目 | 書くこと | 例（`orders.amount`） |
|---|---|---|
| 意味 | 何を表す値か。含むもの・含まないもの | 商品代金の合計。送料・値引きは含まない |
| 単位 | 通貨・税・桁・時間帯 | 円・税抜 |
| 集計方法 | 合計してよいか、平均か、最新値か | 合計してよい |
| 更新頻度 | いつ作られ、いつ変わるか | 注文確定時に 1 回。返品時に別の行で打ち消す |
| 適用範囲 | どの期間・どの対象に有効か | 2024-04 以降の EC 注文。店舗の売上は含まない |
| 責任者 | 定義と値の誤りを誰が直すか | EC 運営チーム |

**集計方法**は見落としやすい。在庫数や口座残高のような「ある時点の量」は、月をまたいで合計すると意味がなくなる。こうした値は、期末の値か平均を使う。

定義書は、表計算のファイルで作ると更新されずに古くなる。コードやデータと同じ場所に置き、**定義のない列が増えたら検査で気づける**ようにする。

```python title="column_defs.py" caption="列の定義を辞書で持ち、定義のない列を見つける" {19,21}
# 列の定義書。「表名.列名」をキーに、意味・単位・集計方法などを書く
COLUMN_DEFS = {
    "orders.order_id":    {"意味": "注文番号", "単位": "-", "集計": "数えるだけ"},
    "orders.customer_id": {"意味": "注文した顧客の番号", "単位": "-", "集計": "数えるだけ"},
    "orders.ordered_on":  {"意味": "顧客が注文を確定した日", "単位": "日付（日本時間）", "集計": "-"},
    "orders.amount": {
        "意味": "商品代金の合計。送料・値引きは含まない",
        "単位": "円・税抜",
        "集計": "合計してよい",
        "更新": "注文確定時に 1 回",
        "責任者": "EC 運営チーム",
    },
}

def undefined_columns(con, table):
    """表にあるのに、定義書に書かれていない列を返す"""
    cols = [row[1] for row in con.execute(f"PRAGMA table_info({table})")]  # 表の列名を一覧で取る
    return [c for c in cols                       # 列を 1 つずつ見て
            if f"{table}.{c}" not in COLUMN_DEFS]  # ★ 定義書にない列だけを残す

print(undefined_columns(con, "orders"))  # ★ 定義が抜けている列を表示
```

```text
['shipped_on', 'invoiced_on', 'shipping_fee']
```

19 行目で、表の列のうち定義書にないものだけを残している。21 行目の結果から、出荷日・請求日・送料の 3 列の定義が抜けていると分かる。これを定期的な検査（テストや CI）に入れておけば、誰かが列を足したときに定義の書き忘れで止まる。

> [!NOTE]
> 指標（売上・粗利・解約率など）の計算式を 1 か所で定義して、利用者が名前で呼び出す仕組みを**セマンティックレイヤー**と呼ぶ。列の定義書の延長にある考え方だ。詳しくは[AIエージェントは「データの意味」を推測できない](2026-09-29-ai-agent-data-design-1-structured.html)の「列に意味を持たせる」で扱った。

## 粒度：1 行が何を表すかを宣言する

「売上テーブル」という名前だけでは、表の設計は決まらない。1 行が何を表すかで、正しい集計方法がまるで変わるからだ。この「1 行が何を表すか」を**粒度**（grain）と呼ぶ。

| 粒度の宣言 | 1 行の例 | この表で答えられる問い |
|---|---|---|
| 1 行 = 注文 1 件 | 注文 1 番、合計 1 万円、送料 500 円 | 注文件数、注文単価 |
| 1 行 = 注文の商品明細 1 つ | 注文 1 番の 2 品目、ノート 3 冊 | 商品別の販売数、併売 |
| 1 行 = 顧客 1 人 × 1 か月 | 顧客 1 番の 2026 年 3 月、購入 2 回 | 月ごとの継続率、解約予測 |
| 1 行 = 商品 1 つ × 1 日の在庫 | ノートの 3 月 31 日の在庫 120 冊 | 在庫の推移（合計ではなく期末値で見る） |

データウェアハウス設計の定番である Kimball の手法では、設計を「業務プロセスを選ぶ → **粒度を宣言する** → 切り口（ディメンション）を決める → 数値（ファクト）を決める」の 4 段階で進める。粒度は列を決めるより**前**に決める。Kimball Group はこれを「粒度の宣言は設計を縛る契約になる」と表現している。

粒度は、元データが持つ**最も細かい単位**（atomic grain）にしておくのが基本だ。月別に集計した表からは、後で「週別に見たい」「商品別に見たい」と言われても戻せない。細かい表からなら、いつでも集計し直せる。

## 粒度を混ぜると合計が黙って膨らむ

粒度の事故は、エラーにならないのがやっかいだ。典型は、**粒度の違う 2 つの表を結合してから合計する**ケースだ。

注文（1 行 = 注文 1 件）に、商品明細（1 行 = 明細 1 つ）をつなぐ。すると注文の行が明細の数だけ複製される。注文側にある送料をそのまま合計すると、明細の数だけ数えてしまう。この現象を**ファンアウト**（行の扇状の増殖）と呼ぶ。

```flow caption="注文 1 件が明細 2 行に結合されると、送料も 2 回数えられる"
direction LR
A[注文 1 番\n送料 500 円] --> B[明細 1：ノート]
A --> C[明細 2：ペン]
B --> D([送料の合計\n1,000 円]):::hl
C --> D
```

```python title="fan_out.py" caption="粒度の違う表を結合して合計すると、送料が膨らむ" {16,23}
con.executescript("""
-- 注文明細の表。1 行 = 注文の商品明細 1 つ
CREATE TABLE order_lines (
  order_id INTEGER,  -- どの注文の明細か
  line_no  INTEGER,  -- 注文の中での明細の番号（1, 2, 3…）
  product  TEXT,     -- 商品名
  qty      INTEGER   -- 数量
);
INSERT INTO order_lines VALUES
  (1, 1, 'ノート', 3), (1, 2, 'ペン', 1),                    -- 注文 1 は 2 明細
  (2, 1, 'ノート', 1), (2, 2, '消しゴム', 2), (2, 3, 'ペン', 5),  -- 注文 2 は 3 明細
  (3, 1, '手帳', 1);                                          -- 注文 3 は 1 明細
""")

wrong = con.execute("""
    SELECT SUM(o.shipping_fee)                     -- ★ 結合したあとで送料を合計（誤り）
    FROM orders o JOIN order_lines l ON l.order_id = o.order_id
""").fetchone()[0]                                 # 結果の 1 行目の 1 列目を取り出す

right = con.execute("""
    SELECT SUM(o.shipping_fee), SUM(l.total_qty)   -- 送料と、明細から作った数量の合計
    FROM orders o
    JOIN (SELECT order_id, SUM(qty) AS total_qty   -- ★ 明細を先に「1 行 = 注文 1 件」へ集計する
          FROM order_lines GROUP BY order_id) l
      ON l.order_id = o.order_id                   -- 粒度が揃ってから結合する
""").fetchone()

print("誤り:", wrong)        # 送料が明細の数だけ数えられた結果
print("正しい:", right)      # (送料の合計, 数量の合計)
```

```text
誤り: 2500
正しい: (1000, 13)
```

15〜18 行目は、結合したあとで送料を合計している。注文 1 は 2 明細、注文 2 は 3 明細なので、500 円 × 2 + 500 円 × 3 = 2,500 円になる。本当の送料は 1,000 円だ。

23 行目では、明細を先に注文単位へまとめている。**結合する前に粒度を揃える**のが直し方の基本だ。数量の合計 13 も、明細から正しく出ている。

> [!WARNING] 1 つの表に違う粒度を混ぜない
> 明細の行と「注文合計」の行を同じ表に入れたり、日別の行と月別の集計行を同じ表に並べたりすると、`SUM` するだけで二重に数えてしまう。Kimball Group も「異なる粒度を同じファクト表に混ぜてはならない。粒度ごとに別の表にする」としている。種類を区別する列（`row_type` など）を足して逃げるのも避けたい。利用者全員に、その列で絞り込むことを覚えさせることになるからだ。

## 宣言した粒度を、検査で守る

粒度は宣言しただけでは守られない。誰かが重複した行を取り込めば、その日から集計は狂う。宣言した粒度は、**その単位で行が 1 つしかないこと**として検査できる。

```python title="check_grain.py" caption="宣言した粒度のキーで重複がないかを調べる" {6,8}
def check_grain(con, table, keys):
    """keys の組み合わせごとに行が 1 つしかないか調べ、重複している組を返す"""
    key_list = ", ".join(keys)              # 例: ["order_id", "line_no"] → "order_id, line_no"
    return con.execute(f"""
        SELECT {key_list}, COUNT(*) AS n    -- キーの組と、その組の行数
        FROM {table} GROUP BY {key_list}    -- ★ 宣言した粒度の単位でまとめる
        HAVING COUNT(*) > 1                 -- 2 行以上ある組だけを残す
    """).fetchall()                         # ★ 空なら粒度どおり

# 明細表の粒度を「注文 1 件」と思い込んでいた場合
print("order_id だけ:", check_grain(con, "order_lines", ["order_id"]))
# 正しい粒度「注文の明細 1 つ」= 注文番号と明細番号の組
print("order_id + line_no:", check_grain(con, "order_lines", ["order_id", "line_no"]))
```

```text
order_id だけ: [(1, 2), (2, 3)]
order_id + line_no: []
```

6 行目で宣言した粒度の単位にまとめ、2 行以上ある組を探している。8 行目の結果が空なら、表は宣言どおりの粒度だ。

1 つ目の結果は、明細表を「注文 1 件の表」だと思い込むと重複が出ることを示している。2 つ目の、注文番号と明細番号の組で調べると重複はない。この組が明細表の粒度であり、次回扱う**主キー**の候補になる。

> [!TIP]
> 粒度は表の説明の 1 行目に書く。「`order_lines`：1 行 = 注文の商品明細 1 つ。キーは `order_id` + `line_no`」。この 1 行があるだけで、結合と集計の事故の多くが防げる。
