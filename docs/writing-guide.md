# 記事の書き方

このブログの記事は「あとで自分が読み返して、手を動かせる」ことを目的にする。
読み物として面白いことより、図・表・コードで仕組みが**分解**されていることを優先する。

---

## 基本方針

### 1. 特定の製品・サービスに寄せない

テーマ自体が特定のサービス（「◯◯ API の使い方」など）でない限り、**どの会社のツールでも通じる一般的な内容**で書く。

- 概念は一般的な言葉で説明する。特定サービスの機能名・API 名・モデル名は、**比較表**か**出典**としてだけ出す
- 各社で呼び名が違うものは、対応表を 1 つ置く（例: Function calling / Tool use / Function calling）
- コードは特定の SDK に依存させない。どうしても必要な部分は **1 か所の窓口（関数）に閉じ込め**、「ここだけ使うサービスに合わせて書く」と明記する
- API キーなしで動かせる**練習用の偽物**（決まった返事をする偽 LLM など）を用意できるなら用意する。読者がその場で動きを確かめられる
- 出典は 1 社に偏らせない。論文・複数企業のガイド・コミュニティ（Zenn・Qiita など）を組み合わせる

### 2. コードは非エンジニアでも読めるように

- **ほぼ全行に日本語のコメント**を付ける。「何をしているか」だけでなく「なぜそうするか」も書く
- 要点の行には `★` を付け、本文の説明と対応させる
- 専門用語はコメントの中で言い換える（例: `# リスト。順番のある入れ物`）
- コードが多い記事は、冒頭に「コードの読み方」の表（`#`・`def`・`[]`・`{}` の意味）を置く
- 変数名・関数名は英語のまま。意味はコメントで補う

```python
for _ in range(max_turns):  # ★ 最大 max_turns 回まで繰り返す（無限ループ防止）
    reply = call_llm(messages, TOOLS)  # LLM に履歴とツール一覧を渡して、次の一手を聞く
    if not reply.tool_calls:           # ★ ツールを頼まれなかったら、それが最終回答
        return reply.text
```

## ファイルとフロントマター

`content/articles/YYYY-MM-DD-<英小文字のslug>.md`

```yaml
---
title: LLMに"ループ"を渡した瞬間、エージェントが生まれる
description: 検索結果と一覧に出る 1〜2 文。何が分かるようになるかを書く
date: "2026-09-29"
updated: ""                 # 大きく直したら日付を入れる
verified: "2026-09-29"      # 記事中の事実（仕様・数値・モデル名）を最後に確かめた日。リサーチした日を入れる
category: AIエージェント     # site.config.mjs の categories にあるものを使う
tags: [LLM, Claude API, Python]
level: [basic, practice, advanced]   # 入門 / 実践 / 発展。扱う範囲をすべて
series: ""                  # 連載にするときだけ同じ名前を入れる
status: published           # 下書きは draft（出力されない）
---
```

新しいカテゴリーを作るときは `site.config.mjs` の `categories` に slug・色・説明を足す。

## タイトル

見やすく、刺さるものにする。ただし中身と違う煽りはしない。

| 型 | 例 |
|---|---|
| 変化の瞬間を言い切る | LLMに"ループ"を渡した瞬間、エージェントが生まれる |
| 誤解を正す | 〇〇は"賢さ"より"設計"で決まる |
| 問い＋手段 | チャットボットとエージェントは何が違うのか：コードで分解する |
| 数字で範囲を示す | 50行から始める / 5つのパターンで整理する |

- 30〜45 字を目安。長くなるなら「——」か「：」で主題と副題に分ける
- 見出し（h2）も同じ考え方で、章を読む理由が分かる言葉にする。「概要」「まとめ」だけの見出しにしない

---

## 構成の型

1. **冒頭（見出しなし）**：誰が何を得られるかを 3〜5 行。その後に `> [!TIP] この記事で分かること` で要点を箇条書き
2. **全体マップ**：`flow` 図で記事の流れか、扱う仕組みの全体像を示す
3. **本論**：基礎 → 実践 → 発展 の順。各章は「なぜ必要か → 仕組み（図/表） → コード → コードの説明 → 落とし穴」
4. **まとめ**：チェックリストか表で要点を再掲。次に読むもの
5. **参考文献**：出典 URL と、いつ時点の情報か

---

## 部品の使い分け

| 伝えたいこと | 使う部品 |
|---|---|
| 処理の流れ、判断の分岐、ループ | `flow` 図 |
| 複数の選択肢の比較、用語の対応 | 表 |
| 動く仕組み | コード＋直後の説明 |
| 補足・注意・よくある失敗 | コールアウト |
| 手順 | 番号付きリスト |

段落は 3〜4 文まで。長い説明は表か箇条書きに分解できないか先に考える。

## 記法

### コードブロック

````markdown
```python title="agent.py" caption="最小のエージェントループ" {3,7-9}
コード
```
````

- `title` ファイル名。`caption` コードの下に出る一行説明。`{3,7-9}` 強調する行
- 対応言語: python / js / ts / bash / json / yaml / diff（ほかは色なしで表示）
- **1 コードブロック = 1 つの要点**。コメントを除いて 40 行を超えるなら分ける
- 直後に「何をしているか」を必ず書く。行番号で参照するなら `{}` で同じ行を強調する
- 記事内の Python は `python -m py_compile` が通ること。省略するときは `...` と明記する
- API キーをコードに書かない。環境変数から読む形にする

### フロー図

````markdown
```flow caption="エージェントループ"
A[ユーザーの依頼] --> B(LLM が考える)
B --> C{ツールを使う?}
C -- はい --> D[ツールを実行]:::hl
D --> B
C -- いいえ --> E([最終回答])
```
````

| 記法 | 意味 |
|---|---|
| `A[文字]` | 四角 |
| `A(文字)` | 角丸 |
| `A{文字}` | ひし形（判断） |
| `A([文字])` | 端点（開始・終了） |
| `-->` / `-- ラベル -->` / `-->\|ラベル\|` | 矢印 |
| `-.->` | 点線の矢印 |
| `==>` | 太い矢印 |
| `:::hl` / `:::muted` | 強調 / 控えめ |
| `direction LR` | 横向き（既定は縦） |
| `\n` | ラベル内の改行 |

戻る矢印（ループ）は自動で図の外側を回る。1 図のノードは 8 個程度まで。
それ以上の図や自由なレイアウトは ```` ```svg ```` に生の SVG を書く。

### コールアウト

```markdown
> [!NOTE]
> 補足

> [!TIP] 独自の見出し
> 役に立つ小技

> [!WARNING]
> よくある失敗
```

種類: `NOTE` `TIP` `IMPORTANT` `WARNING` `CAUTION`

### 記事どうしのリンク

記事ページは `articles/` にあるので、別の記事へは `[タイトル](2026-10-01-other.html)` と書く。

## 事実の扱い

- 数値・仕様・リリース日には出典を付ける。モデル名・SDK の API は執筆時点の公式ドキュメントで確認する
- 「〜と言われている」で済ませない。誰がどこで言ったかを書くか、書けないなら消す
- 公式の主張と、自分の解釈・意見を文で分ける
