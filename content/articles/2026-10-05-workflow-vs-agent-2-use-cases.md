[第 1 回](2026-10-05-workflow-vs-agent-1-basics.html)では、Workflow とエージェントを分ける軸は「処理の流れを誰が決めるか」だと整理した。軸が分かっても、実際の業務を前にすると迷う。請求書処理は AI に読ませるのだからエージェントだろうか。障害調査の報告書づくりまでエージェントに任せるべきだろうか。

この記事では、よくある 8 つの業務を取り上げ、それぞれどちらを選ぶかを流れの図で確かめる。Workflow を選ぶ業務でも AI は使う。違いは、AI が**工程の中で働く**のか、**流れそのものを決める**のかだ。

> [!TIP] この記事で分かること
> - Workflow の中で AI を使うときの置き場所と、AI の出力をプログラムで確かめる方法
> - 定型レポート・請求書処理・定型テスト・データパイプラインが Workflow に向く理由
> - 障害調査・複雑な問い合わせ・不具合の調査・リスク分析がエージェントに向く理由
> - LLM が書いた説明文の数字を、集計結果と突き合わせるコード
> - 同じ調査エージェントが、障害によって違う道筋をたどるコード
> - エージェントで作ったものを Workflow に戻した実例と、その理由

## コードの読み方

コードは Python で、外部のライブラリを使わずに動く。本物の LLM の代わりに**決まった返事をする練習用の偽物**を使うので、API キーなしで動きを確かめられる。要点の行には `★` を付けた。

| 書き方 | 意味 |
|---|---|
| `# 〜` | 説明文（コメント）。プログラムとしては無視される |
| `def 名前(引数):` | 「関数」の定義。決まった手順に名前を付けたもの |
| `return 値` | 関数の結果として、その値を返して終わる |
| `if 条件:` / `for x in 並び:` | 条件に合うときだけ実行する / 1 つずつ取り出して繰り返す |
| `[a, b]` / `{"名前": 値}` | リスト（順番のある入れ物）/ 辞書（名前と値の組の入れ物） |

## AI は「工程の中」でも「流れの上」でも使える

Workflow を選んでも、AI を使わないわけではない。AI の置き場所が違うだけだ。

| AI の置き場所 | AI がすること | 流れを決めるもの | 例 |
|---|---|---|---|
| 工程の中 | 1 つの工程で、読む・書く・分類する | プログラム | 請求書の項目を抜き出す、集計結果を文章にする |
| 流れの上 | 次にどの工程へ進むか、何を使うかを決める | AI | 障害の原因を、ログや数値を見ながら探す |

工程の中で AI を使うときの基本形は、**AI の工程のすぐ後ろに、プログラムの検証工程を置く**ことだ。AI の出力は、もっともらしいが間違っていることがある。間違いが次の工程に流れ込む前に、プログラムで止める。

```flow caption="Workflow の中で AI を使う基本形。AI の後ろに必ず検証を置く"
A([入力]) --> B[前処理\nプログラム]
B --> C(読む・書く・分類する\nLLM):::hl
C --> D{検証\nプログラム}
D -- 合格 --> E[次の工程へ]
D -- 不合格 --> F[差し替え・差し戻し\n人間の確認]
E --> G([出力])
```

## Workflow を選ぶ 4 つの業務

### ① 定型レポートの作成

毎月の売上レポートのように、データを集めて、集計して、グラフにして、文書にする業務だ。

```flow caption="定型レポート。手順・集計方法・出力形式がすべて決まっている"
A([データベースから取得]) --> B[集計]
B --> C[グラフ作成]
C --> D(説明文を書く\nLLM):::hl
D --> E[数字を検証]
E --> F([PDF で出力])
```

| Workflow が向く理由 | AI を使う場所 |
|---|---|
| 処理手順が決まっている | 集計結果を文章で説明する |
| 集計方法が決まっている | グラフの読み方を書く |
| 出力形式が決まっている | レポート全体を要約する |
| 毎月同じ処理を繰り返す | |

ここでの注意は、**集計そのものを LLM にさせない**ことだ。足し算や前月比はプログラムが正確に計算できる。LLM には、プログラムが出した数字を文章にする役だけを渡す。そのうえで、LLM が書いた文章に、集計に無い数字が紛れ込んでいないかを確かめる。

```python title="report_workflow.py" caption="集計はプログラム、文章は LLM、その文章の数字をまたプログラムが確かめる"
import re  # 文章から数字を探す道具

SALES = [  # 元データ。DB から取ってきた想定（店舗, 月, 売上 万円）
    ("渋谷", "8月", 420), ("渋谷", "9月", 480),
    ("梅田", "8月", 390), ("梅田", "9月", 351),
]


def aggregate(rows):
    """★ 集計はプログラムが行う。LLM に足し算をさせない。"""
    by_store = {}  # 店舗 → {月: 売上}
    for store, month, amount in rows:
        by_store.setdefault(store, {})[month] = amount  # 無ければ空の辞書を作ってから入れる
    result = {}
    for store, m in by_store.items():  # 店舗ごとに前月比（%）を計算する
        result[store] = {"9月": m["9月"], "前月比": round((m["9月"] / m["8月"] - 1) * 100)}
    return result


def fake_llm_comment(summary):
    """LLM に集計結果を渡し、説明文を書かせる（練習用の偽物）。わざと 1 つ数字を間違える。"""
    return "渋谷は 480 万円で前月比 +15% と伸びた。梅田は 351 万円で前月比 -10% だった。"


def verify_numbers(text, summary):
    """★ 文章に出てくる数字が、すべて集計結果の中にあるかをプログラムが確かめる。"""
    allowed = {str(abs(v)) for s in summary.values() for v in s.values()}  # 使ってよい数字の集合
    found = re.findall(r"\d+", text)  # 文章中の数字をすべて拾う
    return [n for n in found if n not in allowed]  # 集計に無い数字（＝作り話の疑い）を返す


def build_report(rows):
    summary = aggregate(rows)  # 1. 集計（プログラム）
    comment = fake_llm_comment(summary)  # 2. 文章化（LLM）
    wrong = verify_numbers(comment, summary)  # 3. 検証（プログラム）
    if wrong:  # ★ 1 つでも合わなければ、LLM の文を使わず決まった型の文に差し替える
        print(f"  検証NG: 集計に無い数字 {wrong}。定型文に切り替える")
        comment = " / ".join(f"{s} {v['9月']}万円（前月比 {v['前月比']:+d}%）" for s, v in summary.items())
    return comment  # 4. 出力（ここでは PDF の代わりに文字列を返す）


print(build_report(SALES))
```

```text
  検証NG: 集計に無い数字 ['15']。定型文に切り替える
渋谷 480万円（前月比 +14%） / 梅田 351万円（前月比 -10%）
```

渋谷の前月比は、480 ÷ 420 − 1 で約 14% だ。偽 LLM はわざと「+15%」と書いたので、`verify_numbers` がそれを見つけ、`build_report` は LLM の文章を捨てて定型文に差し替えた。

この形のよいところは、**LLM が間違えても、レポートとしては壊れない**ことだ。文章は少し素っ気なくなるが、数字は正しいまま届く。何回 NG になったかを数えておけば、プロンプトやモデルを見直す目安にもなる。

> [!WARNING] この検証で拾えない間違いもある
> `verify_numbers` は「集計に無い数字」しか見ていない。符号を外して比べているので「-14%」と書かれても通るし、「渋谷は下がった」のような数字の無い誤りも拾えない。検証は、**何を確かめていて、何を確かめていないか**を書き出しておく。足りない分は、増減の向きを別に確かめる、重要な数字は定型文で出す、などで補う。

### ② 請求書の処理

PDF の請求書を受け取り、文字を読み取り、金額・日付・取引先を抜き出して登録する業務だ。第 1 回のコード `invoice_workflow.py` がこの形だった。

```flow caption="請求書の処理。登録する項目も、成功・失敗の条件も決まっている"
A([PDF を受信]) --> B[文字の読み取り\nOCR]
B --> C(項目を抜き出す\nLLM):::hl
C --> D{データを検証}
D -- 合格 --> E([データベースに登録])
D -- 不合格 --> F([担当者が確認])
```

OCR は、画像の中の文字を読み取ってテキストにする技術だ。

| Workflow が向く理由 | AI を使う場所 |
|---|---|
| 登録する項目が決まっている | OCR の読み間違いを文脈から直す |
| 処理の順序が決まっている | 「御請求額」「合計（税込）」など、書き方の違う項目を同じ意味として読む |
| 成功・失敗の条件を書ける | 様式が取引先ごとに違う請求書に対応する |

様式がばらばらな請求書を読めるのは、LLM を使う大きな利点だ。ただし、**金額・登録先・会計データ**のように間違いが許されない値は、LLM の読み取り結果をそのまま信じない。プログラムで確かめる方法を組み合わせる。

| 確かめる値 | プログラムでの確かめ方 |
|---|---|
| 合計金額 | 明細の合計と一致するか。税率から計算した消費税と合うか |
| 取引先 | 取引先マスター（登録済みの取引先の一覧）にあるか |
| 日付 | 日付として正しいか。未来の日付や、極端に古い日付でないか |
| 二重登録 | 同じ請求書番号がすでに登録されていないか |

### ③ 定型的なソフトウェアテスト

テストデータを入れ、API を呼び、期待した値と比べて合否を出す業務だ。

```flow caption="定型テスト。期待値も合否の条件もはっきりしている"
A([テストデータを投入]) --> B[API を実行]
B --> C[期待値と比較]
C --> D[合否を判定]
D --> E([結果を保存])
D -.-> F(失敗したら原因を要約\nLLM):::hl
```

| Workflow が向く理由 | AI を使う場所 |
|---|---|
| テストの手順が決まっている | テストケースやテストコードを作る（実行の前） |
| 期待値がはっきりしている | 失敗したときのエラーログを要約する（実行の後） |
| 合否の条件がはっきりしている | 失敗の原因の当たりを付ける（実行の後） |

テストで AI を使うのは、**実行の前と後**だ。テストの実行そのものに AI の判断を入れると、同じコードでも日によって合否が変わり、テストの意味がなくなる。

### ④ データパイプラインの定期実行

データを取得し、変換し、保存し、キューに積み、処理して、検索できるようにする。夜間に毎日まわすような処理だ。

```flow caption="データパイプライン。実行順も、再試行の条件も決まっている"
A([データを取得]) --> B[変換]
B --> C[ストレージに保存]
C --> D[キューに投入]
D --> E[処理の実行環境で処理]
E --> F([検索基盤に登録])
```

具体的な製品で言えば、ストレージにオブジェクトストレージ（AWS なら S3）、キューにメッセージキュー（同じく SQS）、実行環境にコンテナやサーバーレス関数、検索基盤に全文検索エンジンを使う構成がこれに当たる。どのクラウドでも形は同じだ。

| Workflow が向く理由 | AI を使う場所 |
|---|---|
| 実行の順序が決まっている | 失敗したときのエラーの原因を分析する |
| 再試行の条件を決められる | 大量のログを要約する |
| 成功・失敗をはっきり定義できる | 普段と違う動きを、運用担当者に分かる言葉で説明する |
| 実行結果を監査しやすい | 運用担当者の調査を手伝う |

パイプラインの本体は Workflow のままにし、**失敗したときの調査**に AI を使う。そして、その調査はしばしばエージェント向きの仕事になる。次の節の話だ。

## エージェントを選ぶ 4 つの業務

### ① 障害の原因調査

「夜間バッチが遅くなった原因を調べて」という依頼を考える。原因は最初から分からない。ログを見て、手がかりがあればそれを追い、別の数値を見て、仮説を確かめる。**何を見るかは、前に見たものの中身で決まる。**

```flow caption="障害の原因調査。調べた結果によって、次に見るものが変わる"
A([依頼: 遅くなった原因を調べて]) --> B(次に見るものを選ぶ\nLLM):::hl
B --> C[ログ・数値・DB を見る]
C --> D[仮説と照らし合わせる]
D --> E{原因に届いた?}
E -- いいえ --> B
E -- はい --> F([原因と根拠を報告])
```

| エージェントが向く理由 |
|---|
| 最初から原因が分からない |
| 調べる順番が状況によって変わる |
| 調べた結果によって次の行動が変わる |
| 想定外のケースが起きる |

同じ調査エージェントに 2 つの障害を調べさせ、道筋が変わることを確かめる。

```python title="incident_agent.py" caption="障害の調査。ログの中身によって、DB を見に行くか外部サービスを見に行くかが変わる"
WORLD = {  # 2 つの障害の「現場」。道具を使うと、ここから結果が返る
    "夜間バッチ": {
        "search_logs": "集計ステップが 40 分 → 2 時間に。DB への問い合わせで待ちが多い",
        "get_metrics": "アプリの CPU は 20% で余裕あり",
        "check_db": "orders 表への問い合わせが全件走査。9/30 に索引が削除されている",
    },
    "注文API": {
        "search_logs": "決済サービス呼び出しで タイムアウト が 1 時間に 300 件",
        "get_metrics": "決済サービスの応答時間が 0.3 秒 → 8 秒",
        "check_external": "決済サービスの障害告知: 10:05 から一部で遅延",
    },
}


def fake_llm(history):
    """★ 経過を読んで次の道具を選ぶ（練習用の偽物）。本物の LLM はこの判断を文脈から行う。"""
    text = " ".join(history)  # これまでの結果をまとめて読む
    if "search_logs" not in text:  # まずログを見るのは毎回同じ
        return "search_logs"
    if "DB" in text and "check_db" not in text:  # ★ ログが DB を指していれば DB を見る
        return "check_db"
    if "タイムアウト" in text and "get_metrics" not in text:  # ★ 外部呼び出しの遅れなら数値を見る
        return "get_metrics"
    if "決済サービス" in text and "check_external" not in text:  # さらに相手側の状況を見る
        return "check_external"
    return "answer"  # 原因に届いたと判断したら答える


def investigate(incident, max_steps=6):
    history = [f"依頼: {incident} が遅くなった原因を調べて"]
    for _ in range(max_steps):  # 上限付きのループ
        tool = fake_llm(history)  # 次の一手は LLM が決める
        if tool == "answer":
            return history[-1]  # 最後の発見を原因として返す
        result = WORLD[incident].get(tool, "情報なし")  # 道具を実行（ここでは現場の表を引く）
        print(f"  {tool:<15} {result}")
        history.append(f"{tool}: {result}")  # 結果を経過に積む
    return "上限に達した。担当者に引き継ぐ"


for name in WORLD:
    print(name)
    print("  原因 →", investigate(name))
```

```text
夜間バッチ
  search_logs     集計ステップが 40 分 → 2 時間に。DB への問い合わせで待ちが多い
  check_db        orders 表への問い合わせが全件走査。9/30 に索引が削除されている
  原因 → check_db: orders 表への問い合わせが全件走査。9/30 に索引が削除されている
注文API
  search_logs     決済サービス呼び出しで タイムアウト が 1 時間に 300 件
  get_metrics     決済サービスの応答時間が 0.3 秒 → 8 秒
  check_external  決済サービスの障害告知: 10:05 から一部で遅延
  原因 → check_external: 決済サービスの障害告知: 10:05 から一部で遅延
```

最初にログを見るところまでは同じだ。夜間バッチではログが DB を指していたので DB を調べ、索引（検索を速くするための目次のような仕組み）の削除にたどり着いた。注文 API ではタイムアウトが出ていたので、応答時間の数値を見て、決済サービス側の障害告知まで追った。

夜間バッチの調査では、`get_metrics` を一度も使っていない。**必要のない道具を使わずに済む**のも、Workflow で「ログ → 数値 → DB → 外部」と全部の道具を順に呼ぶ作りとの違いだ。

> [!NOTE] 偽 LLM の if 文と、本物の LLM の違い
> 練習用の `fake_llm` は、「DB」「タイムアウト」という言葉で道具を選んでいる。これを本物の業務でやろうとすると、手がかりの言葉と次に見るべきものの組み合わせを、すべて書き出すことになる。それが書き切れないから LLM に任せる。第 1 回の「次に何をするか分からないならエージェント」は、このことを指している。

### ② 複雑な問い合わせ対応

「先月の請求額がいつもより高い理由を知りたい」という問い合わせだ。第 1 回の `billing_agent.py` がこの形だった。

```flow caption="複雑な問い合わせ。どこに理由があるかは、調べてみるまで分からない"
A([問い合わせ]) --> B(調べる先を選ぶ\nLLM):::hl
B --> C[契約・請求履歴・利用明細\n過去の問い合わせ]
C --> D[情報を比べる]
D --> E{理由が分かった?}
E -- いいえ --> B
E -- はい --> F([回答の案を作る])
```

理由は、追加の作業かもしれないし、料金の改定かもしれないし、割引の期限切れかもしれない。どの情報源に答えがあるかが問い合わせごとに違うので、決まった順に全部を調べるより、手がかりを追う方が早く、回答も具体的になる。

なお、問い合わせ対応の**全体**がエージェントになるわけではない。受付・本人確認・回答の送信は、手順の決まった Workflow で作る。エージェントが担当するのは、理由を調べて回答の案を作るところだ。こうした組み合わせ方は第 3 回で扱う。

### ③ 不具合の調査と修正案

「この不具合の原因を調べて、修正案を作って」という依頼だ。

```flow caption="不具合の調査と修正。テストの結果を見て、修正をやり直すことがある"
A([不具合の報告]) --> B(関連するコードを探す\nLLM):::hl
B --> C[呼び出し元・依存関係を読む]
C --> D[テストを実行・ログを確認]
D --> E[原因を推定して修正案を作る]
E --> F{テストが通る?}
F -- いいえ --> B
F -- はい --> G([修正案を提出])
```

どのファイルを読むべきかは、読んだコードの中身で決まる。修正してテストを流し、落ちれば別の原因を疑う。この「試して、結果を見て、やり直す」繰り返しは、エージェントがいちばん力を発揮する形の 1 つだ。

テストという**自動で合否が分かる仕組み**があることも、エージェントに任せやすい理由になる。Anthropic のガイドも、コーディングを、自動テストで結果を確かめながら繰り返せる仕事として、エージェントが役に立つ例に挙げている。

### ④ 複数の資料を使ったリスク分析

「この取引先のリスクを総合的に評価して」という依頼だ。

| 情報源 | 見るもの |
|---|---|
| 契約書 | 支払い条件、解約の条項、損害賠償の上限 |
| 財務資料 | 売上と利益の推移、負債の大きさ |
| 社内規程 | 取引の審査基準、必要な承認 |
| 過去の取引記録 | 支払いの遅れ、取引額の変化 |
| 問い合わせの履歴 | クレーム、トラブルの記録 |

| エージェントが向く理由 |
|---|
| どの情報が必要かが、最初は分からない |
| 複数の情報源を横断する必要がある |
| 情報どうしの食い違いを確かめる必要がある |
| 調べた結果によって、追加の調査が必要になる |

財務資料で負債の急増が見つかれば、契約書の支払い条件を確かめ直す。過去の取引で支払いの遅れが見つかれば、問い合わせの履歴を探す。1 つの発見が、次に読む資料を決める。

> [!WARNING] リスク分析の「結論」は人間が出す
> エージェントに任せるのは、資料を集めて、発見と根拠を並べるところまでにする。「取引してよいか」の結論は、取引の重みを知る人間が出す。結論まで AI に出させると、根拠の弱い評価が、そのまま意思決定に使われるおそれがある。

## エージェント向きに見えても、型が見えたら固定する

ここまでの 8 つの業務は、分かりやすい例を選んだ。実際には、エージェントで作り始めたものが、運用するうちに Workflow へ寄っていくことがある。

Zenn に公開された事例をいくつか紹介する。数値はどれも各社の報告だ。

| 報告 | 最初の作り | 起きたこと | 変えた作り |
|---|---|---|---|
| ログラス（2025-12） | AI が自分でデータを選んで分析する | データ選びで迷う、時間切れ、出力の品質のばらつき | 業務を 5 つの手順に分け、AI の役割を各手順の中に限定した |
| Finatext（2026-06） | LLM が処理の流れ全体を決める | 大量に実行すると、費用・再現性・追跡のしやすさに問題 | 流れはコードが決め、LLM は候補から選ぶだけにした。費用は約 4 分の 1 になったと報告 |

2 つの報告に共通するのは、**作ってみて初めて、業務の型が見えた**ことだ。エージェントで動かしてみると、毎回だいたい同じ順番で同じ道具を使っていると分かる。そうなったら、その順番をプログラムに書き移し、AI には各工程の中の判断だけを残す。

これはエージェントを使ったことの失敗ではない。手順が分からないうちはエージェントで探り、手順が見えたら Workflow で固める。エージェントを、**業務の型を見つけるための道具**として使ったと考えればよい。

> [!TIP] エージェントのログから型を探す
> エージェントを動かしたら、どの順番で、どの道具を使ったかを記録しておく。何十件か集めて、同じ並びが大半を占めていれば、そこは Workflow に移せる候補だ。並びがばらばらなら、エージェントのままにしておく価値がある。

## 8 つの業務の対応表

| 業務 | 方式 | 決め手 | AI の役割 |
|---|---|---|---|
| 定型レポートの作成 | Workflow | 手順・集計方法・出力形式が決まっている | 集計結果の文章化（数字は検証する） |
| 請求書の処理 | Workflow | 項目と成功・失敗の条件が決まっている | 項目の抜き出し、様式の違いの吸収 |
| 定型テスト | Workflow | 期待値と合否の条件がはっきりしている | 実行の前（テスト作成）と後（失敗の要約） |
| データパイプライン | Workflow | 実行順と再試行の条件が決まっている | 失敗時の原因分析、ログの要約 |
| 障害の原因調査 | エージェント | 見るものが、前に見たものの中身で決まる | 調べる先の選択、仮説の検証 |
| 複雑な問い合わせ | エージェント（調査部分） | 答えのある情報源が問い合わせごとに違う | 調べる先の選択、回答の案の作成 |
| 不具合の調査と修正 | エージェント | 試して、結果を見て、やり直す | コードの探索、修正、テストの繰り返し |
| 複数資料のリスク分析 | エージェント（結論は人間） | 1 つの発見が、次に読む資料を決める | 資料の横断、食い違いの確認、根拠の整理 |

- [ ] Workflow の中で AI を使う工程の後ろに、プログラムの検証を置いた
- [ ] 集計・金額・日付など、プログラムで計算・確認できるものを AI にさせていない
- [ ] 検証で確かめていないことを書き出した
- [ ] エージェントに任せる範囲を「調べて根拠を並べる」までにし、結論や送信は別にした
- [ ] エージェントの行動を記録し、型が見えたら Workflow に移すつもりでいる

表の右側を見ると、エージェントを選んだ業務でも、受付や結論や送信は別の仕組みに任せていることが分かる。次回は、この「Workflow とエージェントを組み合わせる」作り方と、エージェントに付ける制約を、動くコードで組み立てる。
