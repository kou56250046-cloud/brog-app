# 記事作成

「〜について記事を作成して」を受けたときの手順。**構成案の提示で必ず一度止まる。**
執筆ルールと記法は `docs/writing-guide.md` にある。着手前に読む。

## 0. テーマのバックログ

書きたいテーマは `research/backlog.md` に溜める。

| 言われたこと | やること |
|---|---|
| 「〜を書きたいテーマに追加して」「ネタを溜めて」 | 「書きたい」表に 1 行足す。きっかけ・知りたいことも聞けた範囲で書く |
| 「次のテーマ出して」「何を書けばいい？」 | 下の手順で候補を 3 つ出す。**書き始めない** |
| 記事を書き終えたとき | そのテーマを「書いた」表へ移し、記事ファイル名を添える |

「次のテーマ出して」の手順:
1. `research/backlog.md` の「書きたい」と、`content/articles/` の既存記事（title・tags・level）を読む
2. 候補を 3 つ出す。優先は、バックログの優先「高」 → 既存記事の続き（入門しかないテーマの実践・発展、記事内で「別の記事で」と先送りした話題） → 既存記事の `verified` が 6 か月以上前で、情報が古くなっていそうなテーマの更新
3. 各候補に「なぜ今これか」を 1 行、想定レベル、既存記事とのつながりを添える
4. 選ばれたら、この先の 1. リサーチから進める

## 1. リサーチ

テーマを次の観点に分け、WebSearch / WebFetch で調べる。観点ごとに独立しているので並列に投げてよい。

| 観点 | 探すもの |
|---|---|
| 一次情報 | 公式ドキュメント、仕様、リリースノート、論文 |
| 最新動向 | 直近 6〜12 か月の発表・バージョン・変更点 |
| 設計思想 | 作り手や複数企業のエンジニアリングブログが「なぜそうするか」を語ったもの |
| 実践（エンジニアの記事） | **Zenn・Qiita**、企業の技術ブログ（日本語）、個人ブログ・Dev.to 等（英語）。実装例、ハマりどころ、運用の知見、日本語での用語の定着具合 |
| 反対意見 | 限界・批判・向かないケース |

- **Zenn・Qiita は毎回必ず探す**（`site:zenn.dev` / `site:qiita.com` を付けて検索する）。現場のエンジニアが実際に詰まった点と、日本語で通じる言い方が分かる。いいね数・投稿日を見て、古い記事や薄い記事は使わない
- Zenn・Qiita・個人ブログは**二次情報**として扱う。仕様・数値・API の書き方は、公式ドキュメントか論文で裏を取ってから本文に書く。裏が取れないものは「〜という報告がある」と書き、出典を示す
- **出典を 1 社に偏らせない。** 同じ主張が複数の会社・コミュニティから出ているかを確かめ、一般論として書けるものは一般論として書く
- ライブラリや SDK の API は context7 で現行版を確認する。特定の AI サービスを扱う記事（テーマ自体がそのサービス）のときだけ、そのサービスの公式情報（Claude なら `claude-api` スキル）で書き方を確かめる
- 今日の日付を基準に、古い情報には「いつ時点か」を付ける
- 調べた結果は `research/<slug>.md` に残す。形式:

```markdown
# <テーマ> リサーチメモ（YYYY-MM-DD）

## 事実（出典付き）
- 内容 — [出典名](URL)（公開日 / 確認日）

## 主張・意見（誰の）
- 内容 — 誰が / どこで

## 記事に使うコード・図の素材
## 未確認・食い違い
```

## 2. 構成案を提示して止まる

次をチャットに出し、**承認を待つ。** ここで執筆を始めない。

1. タイトル案 3 つ（`docs/writing-guide.md` の型から。それぞれ狙いを一言）
2. 想定読者と、読み終えて何ができるようになるか
3. 見出しの設計図（```` ```hero ````）の案：title、レーンの切り方、主なノード、note に書く設計の要点
4. 章立て（h2 単位）。各章に「狙い」「入れる図・表・コード」「レベル（入門/実践/発展）」
5. 想定分量（文字数とコードの本数）
6. リサーチで分かった論点の食い違い・判断が要る点

修正指示があれば構成案を直して再提示する。

## 3. 執筆

- `content/articles/YYYY-MM-DD-<slug>.md` に書く。`status: published`
- `docs/writing-guide.md` の構成の型・部品の使い分けに従う
- **特定の製品・サービスに寄せない。** テーマが特定サービスでない限り、どの会社のツールでも通じる一般的な内容で書く（詳しくは writing-guide の「基本方針」）
- **コードには非エンジニアでも読める日本語のコメントを付ける。** コードが多い記事では冒頭に「コードの読み方」を置く
- 前付けの直後に ```` ```hero ```` を 1 つ書く（記法と指針は writing-guide の「見出しの設計図」）
- 末尾に「参考文献」節。リサーチメモの出典から、本文で使ったものを載せる
- カテゴリーが `site.config.mjs` に無ければ追加する

## 4. 検証

1. `node build.mjs` がエラーなく終わる
2. 記事中の Python を抜き出して構文確認する:
   ```bash
   node scripts/check-code.mjs content/articles/<file>.md
   ```
   練習用の偽物（偽 LLM など）で動かせる形にしたコードは、実際に実行して記事に書いた出力と一致するかも確かめる
3. `node scripts/serve.mjs` で開き、図・表・コードの表示と、目次・検索でヒットするかを見る
4. 書き上げた原稿を下の表で自己点検し、外れていれば直す
5. 結果（文字数・コード本数・確認したこと）を報告する。コミットは指示があるまでしない

### 書き方の統一チェック

| 項目 | 基準 |
|---|---|
| タイトル | `docs/writing-guide.md` の型のどれか。30〜45 字。引用符は「」 |
| 冒頭 | 見出しなしの導入 3〜5 行 → `> [!TIP] この記事で分かること` |
| 全体像 | 冒頭近くに `flow` 図が 1 枚ある |
| 見出しの設計図 | 前付けの直後に ```` ```hero ```` がある。担い手が付き、note で設計の要点を 1〜3 個示している。ビルドの `hero` 警告が 0 件 |
| 章の流れ | 各 h2 が「なぜ必要か → 仕組み（図/表） → コード → 説明 → 落とし穴」の順 |
| 見出し | 「概要」「まとめ」だけの見出しがない。読む理由が分かる言葉 |
| 中立性 | 特定の会社の製品名・API 名・モデル名が、比較や出典以外で本文に出ていない。コードが特定の SDK に依存していない（依存するなら 1 か所の窓口に閉じ込めている） |
| コード | 1 ブロック 1 要点・コメントを除いて 40 行以内。`title` 付き。直後に説明がある。強調行 `{}` と本文の行番号が一致 |
| コメント | ほぼ全行に、非エンジニアでも分かる日本語のコメントがある。要点に `★` が付いている。専門用語はコメント内で言い換えている |
| 文体 | だ・である調。段落は 4 文以内。比較は表に逃がしている。専門用語は初出で一言説明している |
| 事実 | 数値・仕様・日付に出典がある。出典が 1 社に偏っていない。Zenn・Qiita の内容は一次情報で裏を取った。`verified` にリサーチした日を入れた |
| 末尾 | チェックリストか表のまとめ → 参考文献（日付付き） |
