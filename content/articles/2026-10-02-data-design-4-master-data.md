地域別の売上を出したら、東京が 3 行に分かれた。店舗のレジは「東京」、EC は「13」、海外向けの仕組みは「Tokyo」と書いていたのだ。顧客数も、営業システムと EC で同じ人を別々に数えていたため、実際より多く出ていた。

どちらも SQL の問題ではない。**同じものを指す情報を、システムごとにばらばらに持っている**ことが原因だ。この記事では、業務で繰り返し使う「もの」の情報（マスターデータ）を、どこで正として持ち、どう揃えるかを扱う。

> [!TIP] この記事で分かること
> - マスターデータと、取引のデータ（トランザクション）の見分け方
> - 唯一の正（Single Source of Truth）を、どこに・どの方式で置くか
> - コード体系を設計するときの約束事（意味を埋め込まない・使い回さない・消さない）
> - 「東京」「Tokyo」「13」「TKY」を 1 つのコードに揃える対応表と、未登録の値の見つけ方
> - システムをまたいで同じ顧客を見つける名寄せと、自動で統合してはいけないケース
> - 複数の集計を同じ切り口で並べるための、共通のディメンション

前回の[正規化は守り、非正規化は攻め](2026-10-02-data-design-3-normalization.html)では、1 つのデータベースの中で「1 つの事実を 1 か所に」置いた。今回は同じ考え方を、**システムをまたいで**適用する。

## コードの読み方

コードは Python と SQL で書き、ほぼ全行に日本語の説明を付けた。大事な行には `★` を付けてある。Python に最初から入っている道具だけで動き、上から順に実行すると記事と同じ結果が出る。

| 書き方 | 意味 |
|---|---|
| `# 〜` / `-- 〜` | Python / SQL の説明文（コメント） |
| `def 名前(引数):` | 「関数」の定義。決まった手順に名前を付けたもの |
| `{"キー": 値}` / `辞書.get(キー)` | 辞書（名前と値の組の入れ物） / 辞書から値を引く。なければ `None`（値なし）を返す |
| `unicodedata.normalize("NFKC", s)` | 全角の英数字を半角にするなど、文字の形を揃える |
| `re.sub(r"\D", "", s)` | 文字列から数字以外（`\D`）をすべて取り除く |
| `LEFT JOIN … WHERE 右側 IS NULL` | 相手の表に対応する行が**ない**ものだけを探す書き方 |

## 全体マップ：正を決めて、揃えて、配る

マスターデータの設計は、「どこが正か」を決めるところから始まり、揃えた結果を各所で使えるようにして終わる。

```flow caption="この記事の流れ。正を決め、コードと顧客を揃え、共通の切り口として配る"
A([マスターデータを見分ける]) --> B[唯一の正を決める\nどこで登録し、どこへ配るか]:::hl
B --> C[コード体系を決める\n標準コードと対応表]
C --> D[表記の揺れを揃える\n未登録は止めて知らせる]
D --> E[名寄せする\n同じ顧客を 1 人に]
E --> F([共通の切り口として配る\n適合ディメンション])
```

## マスターデータを見分ける

**マスターデータ**とは、業務の中で繰り返し参照される「もの」の情報だ。[第 2 回](2026-10-02-data-design-2-entity-keys.html)で分けた「もの」と「できごと」のうち、「もの」の側にあたる。

| 種類 | 例 | 変わり方 | 主に参照する側 |
|---|---|---|---|
| 顧客マスター | 顧客番号・氏名・住所・区分 | 引っ越し・改姓・区分の変更 | 注文・請求・問い合わせ |
| 商品マスター | 商品コード・名称・カテゴリー・定価 | 改定・廃番・カテゴリー再編 | 注文・在庫・仕入れ |
| 部門マスター | 部門コード・名称・上位部門 | 毎年の組織変更 | 予算・人事・売上の帰属 |
| 店舗マスター | 店舗コード・所在地・業態 | 開店・閉店・改装 | 売上・在庫・勤怠 |
| コードマスター | 都道府県・支払方法・ステータスなどの区分値 | まれに追加・廃止 | ほぼすべての表 |

マスターデータの誤りは、それを参照する**すべての取引のデータに波及する**。注文 1 件の誤りは 1 件で済むが、商品のカテゴリーが 1 つ誤っていれば、その商品の過去の売上がすべて別のカテゴリーに集計される。投資する価値が高いのはこのためだ。

## 唯一の正（Single Source of Truth）を置く

同じ顧客の住所を、営業システム・EC・請求システムがそれぞれ持っているとする。1 つで住所を変えても、ほかの 2 つは古いままだ。どれを信じればよいかは、誰にも分からない。

これを防ぐ考え方が **Single Source of Truth**（SSOT、唯一の正）だ。**ある情報を正として登録・変更してよい場所を 1 つに決め、ほかはそこからもらう**。ほかのシステムが同じ情報を持つこと自体は構わないが、それは正の写しであり、写しの側で書き換えてはいけない。

```flow caption="正を 1 か所に決め、ほかのシステムは写しを受け取る"
direction LR
A[営業システム\n顧客を登録・変更]:::hl --> M([顧客マスター\n唯一の正])
M --> B[EC\n写しを参照]
M --> C[請求システム\n写しを参照]
M --> D[分析基盤\n写しを参照]
```

正の置き方には、組織の状況に応じたいくつかの方式がある。マスターデータ管理（MDM）の分野では、次の 4 つの型に分けて説明されることが多い。

| 方式 | 正の置き場所 | 登録・変更する場所 | 向く状況 |
|---|---|---|---|
| 登録簿型（registry） | 各システムに置いたまま。対応表だけを中央に持つ | 各システム | まず重複を把握したい。既存システムに手を入れられない |
| 集約型（consolidation） | 中央に集めた「統合版」。分析向け | 各システム（中央は読み取り用） | 分析・レポートの数字を揃えたい |
| 共存型（coexistence） | 中央と各システムの両方。双方向に同期 | 中央でも各システムでも | 業務でも統合版を使いたいが、移行は段階的にしたい |
| 集中型（centralized） | 中央だけ | 中央だけ | 一貫性を最優先する。各システムの改修ができる |

右下へ行くほど一貫性は強くなるが、既存システムの改修が増える。分析の数字を揃えることが目的なら、まず集約型（分析基盤の中で統合版を作る）から始めるのが現実的だ。この記事のコードも、分析基盤の中で揃える前提で書いている。

> [!IMPORTANT]
> 方式を選ぶより先に、**情報ごとに責任者を決める**。顧客の住所は営業部、商品のカテゴリーは商品企画部、というように、誰がその値を正として変更してよいかを決めておく。責任者がいない情報は、どの方式を選んでも揃わない。

## コード体系を設計する：意味を埋め込まない、使い回さない、消さない

マスターには、行を指すための**コード**を振る。コードの体系は一度使い始めると変えにくいので、最初に約束事を決めておく。

| 約束事 | やってはいけない例 | 起きること |
|---|---|---|
| コードに意味を埋め込まない | 顧客コードの先頭 2 桁を担当支店にする | 担当が変わるとコードを変えるか、意味が嘘になる |
| 使い回さない | 廃番になった商品コードを新商品に振る | 過去の売上が新商品の売上として集計される |
| 消さずに廃止する | 使わなくなった区分値を行ごと削除する | 過去の取引が参照先を失う（孤児になる） |
| 桁と型を固定する | `13` と `013` と数値の `13` が混在する | 文字列として比べると一致しない |
| 公的な体系があればそれに合わせる | 都道府県に独自の番号を振る | 外部のデータと突き合わせられない |

都道府県には、JIS X 0401 で定められた 2 桁の**都道府県コード**（01 北海道 〜 47 沖縄県。東京都は 13）という公的な体系がある。国土交通省の 3D 都市モデル（PLATEAU）のデータ仕様のように、国のデータもこの体系を使っている。独自の番号を振るより、こうした体系に合わせたほうが外部データとつなぎやすい。

廃止したコードは、行を消さずに有効期間で表す。コードマスターは、少なくとも次の列を持たせておく。

| 列 | 意味 |
|---|---|
| `code` | コード値。文字列で桁を固定する |
| `name` | 正式名称 |
| `valid_from` / `valid_to` | 有効期間。廃止したら `valid_to` を入れ、行は消さない |
| `sort_order` | 画面や帳票での並び順。コードの大小と並び順を分ける |
| `owner` | このコードの追加・廃止を決める責任者 |

## 表記の揺れを、対応表で 1 つのコードに揃える

システムごとに違う書き方をされた値は、**対応表**（揺れた表記 → 標準コード）で揃える。ポイントは 2 つある。対応表に書く前に、全角・半角や大文字小文字のような機械的な違いを消しておくこと。そして、**対応表にない値を推測で埋めない**ことだ。

```python title="pref_code.py" caption="揺れた表記を、対応表で標準の都道府県コードに揃える" {13,17}
import unicodedata  # 文字の形（全角・半角など）を揃える標準の道具

PREF_MASTER = {"13": "東京都", "14": "神奈川県", "27": "大阪府"}  # 標準コード → 正式名称（JIS X 0401）

ALIASES = {  # 対応表：揃えたあとの表記 → 標準コード
    "東京": "13", "東京都": "13", "tokyo": "13", "tky": "13", "13": "13",
    "神奈川": "14", "神奈川県": "14", "kanagawa": "14", "14": "14",
    "大阪": "27", "大阪府": "27", "osaka": "27", "osk": "27", "27": "27",
}

def normalize(raw):
    """全角→半角、前後の空白の除去、大文字→小文字で、機械的な違いを消す"""
    return unicodedata.normalize("NFKC", str(raw)).strip().casefold()  # ★

def to_pref_code(raw):
    """揺れた表記を標準コードにする。対応表になければ None（推測で埋めない）"""
    return None if raw is None else ALIASES.get(normalize(raw))  # ★ 見つからなければ None

for raw in ["東京", "Tokyo", "13", "TKY", "ＴＯＫＹＯ", " 東京都 ", "東京 都", "横浜"]:
    code = to_pref_code(raw)                                    # 標準コードに変換してみる
    print(repr(raw), "→", code, PREF_MASTER.get(code, "（未登録）"))  # 元の表記・コード・正式名称を表示
```

```text
'東京' → 13 東京都
'Tokyo' → 13 東京都
'13' → 13 東京都
'TKY' → 13 東京都
'ＴＯＫＹＯ' → 13 東京都
' 東京都 ' → 13 東京都
'東京 都' → None （未登録）
'横浜' → None （未登録）
```

13 行目の `normalize` で、全角の「ＴＯＫＹＯ」は「tokyo」に、前後に空白のある「 東京都 」は「東京都」になる。この段階で機械的な違いを消しておけば、対応表には意味の違う表記だけを書けばよい。

一方、「東京 都」（間に空白）と「横浜」（市の名前）は `None` になった。「横浜なら神奈川だろう」と推測で埋めたくなるが、**その推測は誰の責任でもない**。未登録として止め、対応表の責任者に判断してもらう。

### 未登録の値を、黙って捨てない

対応表で揃えた値を集計するとき、内部結合（`JOIN`）を使うと、対応表にない行は**エラーにならずに消える**。どれだけ消えたかを必ず数えて、利用者と責任者に見せる。

```python title="unmapped_report.py" caption="対応表にない値を一覧にし、集計から漏れた割合を出す" {11,19,26}
import sqlite3  # Python に最初から入っている小さなデータベース

con = sqlite3.connect(":memory:")                       # 使い捨てのデータベース
con.create_function("norm", 1, lambda s: None if s is None else normalize(s))  # SQL から normalize を呼べるようにする
con.executescript("""
CREATE TABLE raw_sales (system TEXT, area TEXT, amount INTEGER);  -- 各システムから届いた売上（地域の表記がばらばら）
INSERT INTO raw_sales VALUES ('POS', '東京', 1000), ('POS', 'Tokyo', 2000), ('EC', '13', 1500),
  ('EC', 'TKY', 500), ('EC', 'Kanagawa', 800), ('POS', '横浜', 700), ('EC', '横浜', 300);
CREATE TABLE code_map (alias TEXT PRIMARY KEY, pref_code TEXT NOT NULL);  -- 対応表をデータベースに置く
""")
con.executemany("INSERT INTO code_map VALUES (?, ?)", ALIASES.items())  # ★ 対応表は Python の辞書と同じ中身

unmapped = con.execute("""
    SELECT r.area, COUNT(*), SUM(r.amount)                -- 未登録の表記と、件数・金額
    FROM raw_sales r LEFT JOIN code_map m ON m.alias = norm(r.area)
    WHERE m.pref_code IS NULL                             -- 対応表で見つからなかった行だけ
    GROUP BY r.area
""").fetchall()
print("未登録:", unmapped)                                # ★ 責任者に見せる一覧

by_pref = con.execute("""
    SELECT m.pref_code, SUM(r.amount) FROM raw_sales r
    JOIN code_map m ON m.alias = norm(r.area) GROUP BY m.pref_code
""").fetchall()
total = con.execute("SELECT SUM(amount) FROM raw_sales").fetchone()[0]  # 届いた売上の総額
print("都道府県別:", by_pref, f"漏れ {1 - sum(a for _, a in by_pref) / total:.0%}")  # ★ 集計から漏れた割合
```

```text
未登録: [('横浜', 2, 1000)]
都道府県別: [('13', 5000), ('14', 800)] 漏れ 15%
```

11 行目で、Python の辞書と同じ対応表をデータベースの表にしている。対応表は**コードではなくデータとして**管理し、責任者がコードを書き換えずに行を足せるようにするのが望ましい。

19 行目の一覧が、責任者に渡す「未登録の表記」だ。26 行目は、都道府県別の集計から総額の 15% が漏れていることを示している。この数字を出さずに都道府県別の表だけを渡すと、利用者は全体の 85% しか見ていないことに気づけない。

## 名寄せ：システムをまたいで同じ顧客を 1 人にする

コードの揺れより難しいのが、**同じ顧客が別々の番号で登録されている**問題だ。営業システムでは `C-001`、EC では `u100`。これを同じ人だと突き止めて 1 人にまとめる作業を**名寄せ**と呼ぶ。

名寄せの鍵になるのは、揺れにくく、人ごとに異なる値だ。

| 照合に使う値 | 強さ | 注意 |
|---|---|---|
| メールアドレス | 強い | 大文字小文字・前後の空白を揃えてから比べる。家族で共有している場合がある |
| 電話番号 | 強い | ハイフン・全角を消して数字だけで比べる。会社の代表番号は複数人で共有される |
| 氏名 | 弱い | 同姓同名がいる。表記（髙／高、ｶﾅ／かな）が揺れる |
| 氏名＋生年月日＋住所 | 中程度 | 引っ越しで住所が変わる |

方針は、**強い鍵で一致したものだけを自動でまとめ、弱い鍵だけで一致したものは人の確認に回す**ことだ。誤ってまとめる（別人を 1 人にする）と、ある人の購入履歴や連絡先が別の人に見えてしまう。まとめ損ねる（同じ人が 2 人のまま）よりも、被害が大きい。

```python title="matching.py" caption="強い鍵で自動照合し、氏名だけの一致は確認に回す。結果は対応表に残す" {16,24,26,28,30}
import re  # 文字列のパターン処理の道具

crm = [  # 営業システム（顧客の正とする）
    {"id": "C-001", "name": "山田 太郎", "email": "taro@example.com", "phone": "03-1234-5678"},
    {"id": "C-002", "name": "佐藤 花子", "email": "hanako@example.com", "phone": "06-1111-2222"},
]
ec = [  # EC の会員
    {"id": "u100", "name": "山田太郎", "email": " TARO@Example.com", "phone": None},
    {"id": "u101", "name": "サトウ ハナコ", "email": "h.sato@example.net", "phone": "０６（１１１１）２２２２"},
    {"id": "u102", "name": "佐藤 花子", "email": "sato.h@example.org", "phone": None},
    {"id": "u103", "name": "鈴木 一郎", "email": "ichiro@example.com", "phone": None},
]

def phone_digits(p):
    """電話番号を数字だけにする（全角・ハイフン・かっこを消す）"""
    return re.sub(r"\D", "", normalize(p)) if p else None  # ★ 数字以外を取り除く

by_email = {normalize(c["email"]): c["id"] for c in crm}   # メール → 営業システムの顧客番号
by_phone = {phone_digits(c["phone"]): c["id"] for c in crm} # 電話番号 → 顧客番号
by_name  = {normalize(c["name"]).replace(" ", ""): c["id"] for c in crm}  # 空白を除いた氏名 → 顧客番号

xref, review = [], []                                      # 名寄せの対応表 / 人が確認する一覧
for u in ec:
    if (m := by_email.get(normalize(u["email"]))):          # ★ 1. メールが一致したら自動で同一人物
        xref.append((m, "EC", u["id"], "email"))
    elif (m := by_phone.get(phone_digits(u["phone"]))):     # ★ 2. 電話番号が一致しても自動で同一人物
        xref.append((m, "EC", u["id"], "phone"))
    elif (m := by_name.get(normalize(u["name"]).replace(" ", ""))):  # ★ 3. 氏名だけの一致は自動でまとめない
        review.append((m, "EC", u["id"], "name"))
    else:                                                   # ★ 4. どれとも一致しなければ新しい顧客
        xref.append((f"NEW-{u['id']}", "EC", u["id"], "new"))

print("対応表:", xref)
print("要確認:", review)
```

```text
対応表: [('C-001', 'EC', 'u100', 'email'), ('C-002', 'EC', 'u101', 'phone'), ('NEW-u103', 'EC', 'u103', 'new')]
要確認: [('C-002', 'EC', 'u102', 'name')]
```

照合は 24〜31 行目の 4 段階で、強い鍵から順に試す。`u100` はメールの大文字と前の空白が違うだけなので、揃えてから比べれば一致する。`u101` はカタカナの氏名でメールも違うが、全角・かっこ付きの電話番号を 16 行目で数字だけにすると一致する。

`u102` は氏名が完全に同じだが、メールも電話番号も違う。同姓同名の別人かもしれないので、自動ではまとめず確認の一覧に回した。`u103` はどれとも一致しないので、新しい顧客として番号を振る。

> [!WARNING] 名寄せの結果は「対応表」として残し、元の番号を消さない
> 名寄せの結果は、元のデータを書き換えるのではなく「統合後の番号・システム名・元の番号・照合の根拠」の対応表として残す。後から「この 2 人は別人だった」と分かったとき、対応表の行を直すだけで戻せる。元の番号を統合後の番号で上書きしてしまうと、戻す手がかりがなくなる。

## 複数の集計を、同じ切り口で並べる：適合ディメンション

マスターを揃える最終的な目的は、**別々の業務の数字を、同じ切り口で並べられるようにする**ことだ。売上（POS）と在庫（倉庫システム）を、同じ「店舗」「地域」で並べたい。このとき、両方の集計が同じ店舗ディメンションを使っていなければ、地域の区切り方が食い違って並べられない。

Kimball の手法では、複数のファクト表で同じキー・同じ属性・同じ値を共有するディメンションを**適合ディメンション**（conformed dimension）と呼ぶ。マスターデータを 1 か所で揃え、それを各ファクトが共通で使う形だ。

```python title="conformed.py" caption="売上と在庫を同じ店舗ディメンションで地域別に集計し、横に並べる" {10,12,17}
con.executescript("""
CREATE TABLE dim_store (store_id TEXT PRIMARY KEY, store_name TEXT, pref_code TEXT);  -- 共通の店舗の切り口
INSERT INTO dim_store VALUES ('S1', '新宿店', '13'), ('S2', '渋谷店', '13'), ('S3', '横浜店', '14');
CREATE TABLE fct_sales (store_id TEXT, sold_on TEXT, amount INTEGER);          -- 売上。1 行 = 店舗×日
INSERT INTO fct_sales VALUES ('S1', '2026-04-30', 5000), ('S2', '2026-04-30', 3000), ('S3', '2026-04-30', 2000);
CREATE TABLE fct_inventory (store_id TEXT, snapshot_on TEXT, stock INTEGER);  -- 在庫。1 行 = 店舗×日の残高
INSERT INTO fct_inventory VALUES ('S1', '2026-04-30', 40), ('S2', '2026-04-30', 10), ('S3', '2026-04-30', 30);
""")
rows = con.execute("""
    WITH s AS (SELECT d.pref_code, SUM(f.amount) AS sales     -- ★ 売上を地域別に先に集計
               FROM fct_sales f JOIN dim_store d USING (store_id) GROUP BY d.pref_code),
         i AS (SELECT d.pref_code, SUM(f.stock) AS stock      -- ★ 在庫も同じディメンションで地域別に集計
               FROM fct_inventory f JOIN dim_store d USING (store_id)
               WHERE f.snapshot_on = '2026-04-30'             -- 在庫は合計でなく、ある日の残高で見る
               GROUP BY d.pref_code)
    SELECT s.pref_code, s.sales, i.stock
    FROM s JOIN i USING (pref_code)                           -- ★ 粒度（地域）が揃ってから並べる
    ORDER BY s.pref_code
""").fetchall()
print(rows)
```

```text
[('13', 8000, 50), ('14', 2000, 30)]
```

10 行目と 12 行目で、売上と在庫を**同じ店舗ディメンション**を通して地域別に集計している。17 行目で、地域という同じ粒度になってから横に並べる。[第 1 回](2026-10-02-data-design-1-purpose-grain.html)の「結合の前に粒度を揃える」と同じ考え方だ。

在庫は「ある時点の残高」なので、日をまたいで合計してはいけない。14 行目で特定の日に絞っているのはそのためだ。

> [!NOTE]
> もし売上側は「東京・神奈川」、在庫側は「関東」という別の地域区分を使っていたら、この 2 つの集計は並べられない。どの部署も同じ店舗ディメンションを使うように揃えることが、マスターデータ管理の目に見える成果になる。

## 設計チェックリスト

| 段階 | 確かめること |
|---|---|
| 見分け | 業務で繰り返し参照される「もの」をマスターとして挙げたか。それぞれの責任者が決まっているか |
| 唯一の正 | 情報ごとに、正として登録・変更してよい場所が 1 つに決まっているか。写しの側で書き換えていないか |
| 方式 | 目的（分析の数字を揃えたいのか、業務も揃えたいのか）に合った置き方を選んだか |
| コード体系 | コードに意味を埋め込んでいないか。使い回さず、消さずに有効期間で廃止しているか。公的な体系があれば合わせたか |
| 揺れ | 機械的な違い（全角・空白・大文字小文字）を消してから対応表で揃えているか。対応表をデータとして管理しているか |
| 未登録 | 対応表にない値を推測で埋めず、一覧にして責任者に渡しているか。集計から漏れた割合を出しているか |
| 名寄せ | 強い鍵だけで自動統合し、弱い鍵だけの一致は人の確認に回しているか。結果を対応表として残し、元の番号を消していないか |
| 共通の切り口 | 複数の集計が、同じディメンションを使っているか。並べる前に粒度を揃えているか |

次回は、マスターの値が**変わったとき**を扱う。顧客が引っ越したら、過去の注文は新しい住所で集計すべきか、当時の住所で集計すべきか。現在値と履歴の持ち方、更新履歴の残し方、そして DWH の定番である SCD（ゆっくり変わる属性の持ち方）を見ていく。
